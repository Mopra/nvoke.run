# nvoke v1 spec

nvoke is a lead finder sold to paying customers. A web app at nvoke.run/app is the front door (see "Web app"), nvoke Desktop (Electron) is the premium native app with the power tools, and the same features are open to code and AI agents through a REST API and an MCP server (see "API and agents"). The user starts a search, the backend on our VPS finds companies, crawls their websites, extracts email addresses and checks that they can receive mail. The user browses, filters and exports the results.

## Search kinds

| kind | user gives | where companies come from |
|---|---|---|
| `local` | niche + location, e.g. "dentists" + "Copenhagen" | OpenStreetMap: Nominatim to resolve the location to a bounding box, Overpass to find matching businesses (by tag and name) that have a `website`. Free, no key. When those fall short of the limit, places that match the niche by tag but list no website are looked up on Brave as "<name> <city>" (`addr:city`, else the location) in the place's country, one request each through the same cache as `web`, at most 50 per search (`MAX_PLACE_LOOKUPS`), skipping names already found or looked up (a chain has one site). The result that is the place's own site is crawled: not a platform, directory, webmail or .edu/.gov domain, and its brand label is the name run together, holds every distinctive word of the name or two long ones (the niche's words, their plurals, the city and stop words left out; a one word name must start the label), see `pickPlaceSite` in `@nvoke/shared/crawl`. There is no fall back to the top result, so a place without a matching result is skipped. `docs/research/crawl-benchmark.md` measures it. The public Overpass instances (`OVERPASS_URL`, six by default) are often busy or down: a query tries each in turn, then two more rounds after 5 and 20 seconds, within 5 minutes. When they all stay down, or all of that finds fewer places than the limit, a Brave web search for "<niche> in <location>" (scoped to the place's country) fills the rest, with the same costs and rules as `web`. An unknown location still fails with `location_not_found`. |
| `web` | keyword, optional country | Brave Search API (`BRAVE_SEARCH_API_KEY`), with Mwmbl as the free fallback (`FREE_SEARCH`). Take result domains, drop big platforms (social networks, marketplaces, Wikipedia, news). Paid per request, see "Source costs". |
| `launches` | optional keyword filter, time window | Product Hunt and Hacker News "Show HN" (port from `../probe/apps/worker/src/sources`). |
| `domains` | a list: domains, URLs, email addresses or company names, up to the search limit, optional country | The list itself. Domains (and the domain of an email address) go straight to the crawl, at no cost; webmail addresses are skipped. Each name costs one Brave request (the first result page, through the same cache, rate limit and refusal rules as `web`, see "Source costs"); platform and webmail domains are dropped and the result whose domain looks most like the name wins (legal words such as ApS and Inc ignored, æ ø å folded), else the first usable one of the top 3, else the name is skipped. `splitList` in `packages/shared/src/lists.ts` turns pasted text into items. |
| `drop` | nothing: a drop makes it (see "Drops") | The feed the worker collects around the clock. |
| `icp` | "Describe your customer": who they sell to in plain words (`description`), optionally what they sell (`product`), `countries` and `locations` | A plan Claude makes from the words, run on Brave, on the list pages it finds and on OpenStreetMap, each candidate given a first look for fit and, when its crawl found someone to check, a second look after the crawl. See "Describe your customer". |

Each source is an adapter with the same interface, so more can be added later:

```ts
interface SourceAdapter<P> {
  kind: SearchKind
  find(params: P, ctx: { limit: number; signal: AbortSignal; log: Logger }): AsyncIterable<FoundCompany>
}
type FoundCompany = { name: string; website: string; source: string; sourceRef?: string; location?: string; phone?: string; category?: string; fit?: number; fitReason?: string; title?: string; snippet?: string }
```

## Pipeline per search

1. API inserts a `searches` row (`queued`) and a `find` job.
2. Worker runs the source adapter, inserts `companies` rows (deduped per search by normalized domain), and enqueues one `crawl` job per company. It stops at the search's `limit` (default 100, at most the plan's search limit, see "Plans"). A `domains` search has as many as its list: the API cuts the list to `limit` when one is given and stores the length as the limit. Its find job may run 30 minutes, since names are looked up at Brave's rate. An `icp` search's limit counts the companies fit keeps after the crawl: at the limit its find waits up to 2 minutes (`FIND_SETTLE_MS`) for the crawls and fit of its companies, and finds on in the place of those turned down (`dropped` in the adapter's context).
3. `crawl`: skip the company if its domain is suppressed (see "Privacy"). Otherwise check the shared cache (`domains`): a fresh row (`recheck_at` in the future) is reused when the last crawl found no personal addresses, or when it failed or was blocked. Reuse copies the domain's cached generic addresses (`domain_emails`) into this search's `emails`, minus suppressed ones, without fetching anything. In every other case crawl again: fetch the homepage (trying plain http and the www twin when the given address fails, and following a meta refresh or script redirect unless it leads to a platform) plus likely pages (contact, about, team, impressum, privacy, legal, in a dozen languages) from its links, from its sitemap when it links to fewer than two, and guessed paths (`/contact`, `/kontakt`, `/about`, `/impressum` and more) while no address on the company's own domain has turned up, max 8 pages (sitemap files count) and 2 MB per company. Respect robots.txt. Identify as `nvokebot/1.0 (+https://nvoke.run/bot)`. At most 1 request per second per domain and a global concurrency cap. Extract emails from text, `mailto:` links, Cloudflare email protection, JSON-LD, schema.org microdata and hCard, contact form recipients, vCards and the usual obfuscations ("name [at] domain [dot] com", "(a)", split attributes, reversed text). `docs/research/crawl-benchmark.md` measures every change to this step. Port and extend `../probe/apps/worker/src/contact/extract.ts`. Drop image filenames, placeholder addresses (example.com, sentry, wixpress, etc.) and addresses on unrelated domains unless they are the only ones found. Classify each address `generic` (role mailbox) or `personal` (always for webmail such as gmail.com). Then drop suppressed addresses, store all remaining addresses in this search's `emails`, upsert the `domains` row (`recheck_at` 90 days after a crawl, 7 days after a failed or blocked one, `has_personal` set when personal addresses were found), upsert the generic addresses into `domain_emails` (`first_seen` never changes, `last_seen` moves to now) and delete the domain's cached addresses this crawl no longer found. It also replaces the domain's kept page text (`domain_pages`, for openers): the homepage and up to two more pages it read, skipping contact, team and legal pages, 3,000 characters of visible text each, with every email address taken out. Personal addresses never go into the shared cache. The crawl ends in one of five outcomes: `done`, `failed` (unreachable, or an error answer), `blocked` (robots.txt or a suppression keeps us out), `refused` (the homepage answered 401, 403, 429 or 503, or served a bot challenge such as "Just a moment..." or a CAPTCHA: the site refuses our servers) and `js_only` (the crawl finished without an address and the homepage is an app shell: under 200 characters of visible text with scripts, or a `noscript` that asks for JavaScript). `refused` and `js_only` are cached for 7 days like a failure. The desktop app reads those, and `done` sites without an address, from the user's computer (see "Local render crawl"). An `icp` company (`companies.fit_state = 'gate'`) whose crawl found an address that could ever be checked (not off target, and a role inbox only when it could be the fallback or the search checks inboxes) or a named person who is not off target (`needsFit`) gets no check and no people job yet: it waits for fit's second look (`fit_state = 'pending'`, see "Describe your customer"). Addresses the local render crawl hands in for such a company wait the same way.
4. `verify`: per email, check syntax, common freemail typos (`gmial.com` and the like, `invalid`), the disposable domain list and MX records (a domain whose MX belongs to a parking service is `invalid`), then an SMTP RCPT probe without sending (EHLO, MAIL FROM, RCPT TO, QUIT). The same session asks about two random addresses on the domain; if the server accepts either, the domain is `catch_all`. A 4xx reply (greylisting), a mail server we cannot connect to or that stalls mid session are not cached: the verify job is queued again 10 minutes later, twice, before the address settles as `unknown`. A check we could not make on our side is not a retry and never settles for that reason: every lane at its budget (`smtp_paced`), port 25 blocked on every IPv4 lane, Google or Microsoft refusing or stalling our connection (`smtp_throttled`, they do that when one IP probes many of their domains), or the job running out of time while it waited for the mail server. It goes back in the queue in the same job row, after 1 minute when only the slots were taken, else 10 minutes, doubling each time up to 2 hours, with up to 20% jitter, and settles `unknown` (reason `capacity_deadline`) only 48 hours after its first such wait. Such a check is pending like any other: the search keeps running and `queuedChecks` (`src/worker/queue.ts`) counts it for the escalation logic. Sessions go out over three kinds of lane, in order: IPv6 when the MX host has an AAAA record (Google's do, Microsoft's `mail.protection.outlook.com` mostly do not), then this VPS's IPv4, then each relay's IPv4 (`SMTP_RELAYS`). Hostinger allows 5 port 25 connections a minute per VPS IPv4 address, so each IPv4 lane opens at most `SMTP_PROBES_PER_MINUTE` a minute (this VPS gives the free tools their share); IPv6 is not throttled. The per provider limit is shared by all lanes, so no provider sees more than one well behaved sender. A lane counts as blocked only when its connections fail at 5 different MX providers in a row and canary connections over that lane to Gmail's, iCloud's and Yahoo's MX fail too. That lane alone then pauses for 10 minutes and the operator gets an alert naming it (`smtp-port25-blocked`, at most every 6 hours); a relay whose tunnel is down is left alone for a minute. Every `unknown` result and every requeue is logged with its reason and search id. The people job follows the same rule: a probe we could not make on our side goes back in the same job row with the same backoff, never as its one retry, and after 48 hours of such waits the job ends with those people left without an address; a real server answer keeps its one retry. Cache results per address for 30 days (the retention of `email_checks`), `unknown` for 1 day. A charged address was confirmed within the month; the owner chose fewer repeat probes over a weekly recheck (docs/research/cost.md). A `valid` result is charged against the user's plan in the same transaction (see "Plans"); every other result is free.
   Cached addresses go through the same verify step and count toward the quota the same way: a user pays per valid verification, wherever the address came from.
   Checks go to named people (`checkPolicy` in `src/leads/check-policy.ts`, applied by the verify job and once more when a result is recorded). A named person with a title or a seniority who is not off target is checked at once. Every other address waits only for those, so no waiting address waits for another: an unnamed personal address (no first and last name: max@, mh@) waits until the company's named people settle and is left unchecked (`emails.skipped = 'unnamed'`) once any named person is valid. A named person with no title and no seniority (most often a name read from the address) waits until the titled named people settle and is left out (`skipped = 'untitled'`) once one of the company's decision makers or sales, growth, marketing, business development or partnership people is valid; with none of those valid it is checked. People in functions a seller does not write to are never checked (`skipped = 'off_target'`), whatever else the company has: HR, recruiting, data protection, customer support and success, bookkeeping and finance, office staff, assistants and interns in any team (an assistant to the CEO or the Geschäftsführung too), and C level or VPs in finance, people or customer success (CFO, CHRO, Chief People Officer, VP Customer Success) unless the title is commercial (`isOffTargetTitle` in `@nvoke/shared/crawl`). A founder is never off target. Role inboxes (`kind = 'generic'`) are not checked by default, with one exception: a company with no valid personal address gets one fallback inbox checked. It is the best of its role inboxes by `inboxRank` (sales@ first, then hello@, contact@, info@, office@, then unlisted ones, then support@, billing@, jobs@ and press@, privacy@ and legal@ last, no-reply and postmaster never; ties go to the first address). It waits until every personal address that is not off target settles, so a named person is always preferred, and it is checked only when none of them is valid. Only one per company is checked: once one has a result, or while a better one exists, the rest stay unchecked, hidden and free (`skipped = 'role_inbox'`). A valid fallback inbox is charged like any verified email and shown like any other result. The search can ask for all of its role inboxes (`searches.check_inboxes`, default false, set by `checkInboxes` on create or on `PATCH /v1/searches/:id`, where switching it on clears `skipped` on the search's role inboxes skipped for that reason and queues their checks at priority -10, after every named person). With it on, every role inbox waits for the named people and is left out once any personal address is valid. A waiting check goes back in the queue marked `deferred` and is woken the moment a check of its company settles or its people job ends (5 minutes at the latest); after 12 defers or 30 minutes it is decided without waiting more. An address that became unnecessary while it was being checked is recorded skipped, not charged. A skipped address counts as settled for `lead.ready` and for finishing the search, and Search more does not queue it again.
   A personal address nobody on the site was printed for still names its owner when its local part is first.last, first_last or first-last and both parts read as a name (the first a common first name or one the site printed): `first_name` and `last_name` are filled, `title` stays empty and `confidence` is 80 instead of 90. A lone first name (max@) or a double first name (anne-marie@, karl-heinz@) stays unnamed unless a printed person matches it, and a name read this way never teaches the people job a domain's pattern. A "person" that is the company itself is dropped when the name has no first name in it (Agence Nova on agencenova.com) or is the company's whole name with no title; a titled founder the company is named after (Peter Jensen, Founder, at Peter Jensen ApS) is kept.
   The people step asks Haiku only when the rules leave names unread. The crawl reads people from schema.org (JSON-LD, microdata, RDFa), team card markup (a role field and the one name in its card), imprint labels and name and title lines, with titles in English, the Nordic languages, German, Dutch, French, Spanish, Italian, Portuguese, Polish and Finnish. When it finds no decision maker, `needsPeopleLlm` checks the people pages for names it did not read. One name next to a founding verb or a decision maker's title is enough; otherwise there must be at least two, each a common first name or with a title word around it. Haiku then reads only the lines around those names (`peopleExcerpt`, at most 3,000 characters across pages, "..." where lines are left out), without reasoning, with at most 20 people and 1,500 output tokens. Every name it gives must still be printed on the full page, with its title printed near it. It reads during the crawl, before fit; the people job of an `icp` company is queued only once fit keeps the company.
5. When all jobs for a search are finished, the search becomes `done` (or `failed` with an error).
6. A search grows as a list: once it ended (`done`, `failed` or `canceled`), `POST /v1/searches/:id/more` runs it again with new params of the same kind (a wider area, another keyword, more items). The new params become the search's, its `limit` becomes the companies it holds plus the new limit, the run is appended to `runs` and a find job goes in the queue. The unique `(search_id, domain)` keeps companies it already holds out, so a run only adds what is new; counters keep counting. Webhooks send `lead.ready` for the new leads; `search.finished` goes out once per search, after the first run that ends `done` or `failed`. The new run also queues the crawls and checks a cancel or quota stop left undone, and waits (409 `search_running`) while a canceled run's find job is still stopping. Each run's find asks its source for the search's whole limit, since companies the search already holds are skipped.

Everything is a row in a Postgres `jobs` table claimed with `FOR UPDATE SKIP LOCKED`. No Redis. Retries use exponential backoff, max 3 attempts. The worker handles SIGTERM cleanly. The worker also runs the retention purge (`apps/server/src/leads/retention.ts`) at start and then hourly (see "Privacy").

## Data model (Postgres, public schema, RLS enabled with no policies)

- `accounts`: `clerk_user_id` pk, `plan` (a key from `packages/shared/src/plans.ts`, default `free`), `plan_synced_at` (last read from Clerk Billing), `created_by` (`human` | `agent`), `agent_name`, `claimed_at` (null while an agent-created account is unclaimed), `created_at`. Created on first authenticated request, or by agent sign-up.
- `api_keys`: `id`, `clerk_user_id`, `name`, `key_hash` (sha256, the key is never stored), `prefix` (shown in lists), `origin` (`user` | `agent_signup`), `created_at`, `last_used_at` (written at most once a minute), `revoked_at`.
- `agent_signups`: one row per sign-up attempt for the rate limits: `ip_hash` (sha256, never the IP), `email_domain`, `clerk_user_id`, `created_at`. Kept 30 days.
- `ongoing_budget`: `day` (UTC date) pk, `reserved`: the paid Brave requests ongoing searches' daily rounds reserved that day.
- `searches`: `id` uuid, `clerk_user_id`, `kind`, `params` jsonb, `limit` int (both the latest run's), `runs` jsonb (every run in order: `params`, `limit`, `foundBefore`, `createdAt`, and `trigger` (`escalate` or `ongoing`) on runs nvoke started itself, with the `braveBudget` an ongoing round reserved; none for a drop's), `stage` and `stage_note` (the live progress line), `ongoing` (default false), `plan` jsonb (an `icp` search's plan, see "Describe your customer"), `status` (`queued` | `running` | `done` | `failed` | `canceled`), `error`, counters (`companies_found`, `companies_crawled`, `emails_found`, `emails_valid`, and `source_requests` and `source_cache_hits` from "Source costs"), `check_inboxes` (role inboxes are checked only when true, see step 4), `created_at`, `started_at`, `finished_at`.
- `companies`: `id`, `search_id`, `clerk_user_id`, `name`, `domain`, `website`, `source`, `source_ref`, `location`, `phone`, `category`, `fit` and `fit_reason`, `fit_state` (`icp` only: `gate` after the first look, `pending` while its checks wait for the second, `kept`; null for other kinds), `crawl_status` (`pending` | `done` | `failed` | `blocked` | `refused` | `js_only`), `crawled_at`, and the local render crawl's state: `local_crawl` (null, `claimed`, `done`, `failed` or `blocked`), `local_claimed_until`, `local_attempts`, `local_crawled_at`, and the opener (see "Openers"): `opener_status` (null, `queued`, `done`, `none` or `failed`), `opener`, `opener_source_url`, `opener_quote`, `opener_at`. Unique `(search_id, domain)`.
- `emails`: `id`, `company_id`, `search_id`, `clerk_user_id`, `address` (lowercase), `kind` (`generic` like info@/contact@, or `personal`), `source_url`, `verification` (`valid` | `invalid` | `risky` | `catch_all` | `unknown`), `checked_at`, `skipped` (`role_inbox` | `off_target` | `unnamed` | `untitled` when left unchecked on purpose, see step 4). Unique `(company_id, address)`.
- `email_checks`: cache keyed by `address`, with `verification`, `mx_host`, `checked_at`.
- `usage`: `clerk_user_id`, `period` (yyyy-mm), `emails_verified`.
- `billed_emails`: `clerk_user_id`, `address`, `period`, `billed_at`. Primary key `(clerk_user_id, address)`: every address a user was ever charged for.
- `domains`: shared crawl cache, one row per domain: `domain` pk (lowercase), `crawl_status` (`done` | `failed` | `blocked` | `refused` | `js_only`), `crawled_at`, `has_personal` (the last crawl found personal addresses, which are not cached), `recheck_at` (after this the next search that finds the domain crawls it again).
- `domain_emails`: generic addresses only, shared across users: `domain` (fk to `domains`, cascade), `address` (lowercase), `source_url`, `first_seen` (fixed at first collection, drives retention), `last_seen`. Primary key `(domain, address)`.
- `domain_pages`: the visible text the last real crawl kept per domain, shared across users, for openers: `domain` (fk to `domains`, cascade, so retention, opt-out and erasure take it along), `url`, `title`, `description`, `text` (at most 3,000 characters, no email addresses), `fetched_at`. Primary key `(domain, url)`.
- `suppressions`: opted-out addresses and domains, stored only as `hash` pk (sha256 hex of the lowercased address, or of `'domain:' || registrable domain`), `kind` (`address` | `domain`), `source` (`opt_out_page` | `email` | `bot_page` | `admin`), `created_at`. Kept forever. Code in `apps/server/src/leads/suppression.ts`.
- `web_search_cache`: Brave result pages keyed by `(query, country, page)` (free search pages under the country `mwmbl:<country>`): `companies` jsonb (name, website, result URL only, never the raw response), `more` (Brave has a next page), `fetched_at`.
- `alerts_sent`: `key` pk, `sent_at`. When each operator alert last went out (see "Source costs").
- `source_pauses`: `source` pk (`brave`, `free_search`), `reason`, `paused_at`, `until`.
- `jobs`: `id`, `type` (`find` | `crawl` | `verify` | `opener` | `people` | `write` | `fit`), `payload` jsonb, `status`, `attempts`, `run_after`, `locked_at`, `last_error`.
- `feed_items`: launches collected for drops: `id` (identity, the drop cursor), `source`, `source_ref` (unique together), `name`, `website`, `domain`, `tagline`, `description`, `tags`, `location`, `launched_at`, `discovered_at`, `search_text` (lowercased name, tagline, description and tags). No addresses.
- `feed_sources`: one row per collector: `source` pk, `last_run_at`, `last_ok_at`, `last_error`, `last_found`, `last_added`.
- `drops`: `id`, `clerk_user_id`, `name`, `keyword`, `sources`, `daily_limit`, `enabled`, `cursor` (highest `feed_items.id` already considered), `next_run_at`, `last_delivered_at`, `created_at`. `searches.drop_id` points at the drop that made a search (set null when the drop is deleted).
- `webhooks`: `id`, `clerk_user_id`, `url`, `secret`, `events`, `scope` (`all` | `drops`), `drop_id` (cascade), `enabled`, `disabled_reason`, `last_success_at`, `last_failure_at`, `last_error`, `created_at`. See "Webhooks".
- `webhook_deliveries`: `id` (the `webhook-id` header), `webhook_id` (cascade), `event`, `search_id` (cascade), `company_id` (cascade, `lead.ready` only), `status` (`pending` | `delivered` | `failed` | `skipped`), `attempts`, `next_attempt_at`, `locked_until`, `last_status`, `last_error`, `created_at`, `delivered_at`. Unique `(webhook_id, event, search_id, company_id)`.
- `ai_usage`: one row per Claude call: `id`, `clerk_user_id` (cascade), `task`, `model`, `input_tokens`, `output_tokens`, `cache_read_tokens`, `cache_write_tokens`, `cost_usd`, `created_at`. No prompt or response text. See "Claude".
- `site_profiles`: one per account: `clerk_user_id` pk (cascade), `website` (as read, after redirects), `domain`, `profile` (jsonb, `SiteProfileFields`), `suggestions` (jsonb, `SuggestedSearch[]`), `pages` (jsonb, the URLs read), `icon_url`, `image_url`, `created_at`, `updated_at`. See "Site profile".
- `site_shots`: the homepage screenshot of a site profile, at most one per account: `token` pk (32 random bytes, base64url), `clerk_user_id` (cascade), `image` (JPEG bytes), `created_at`.
- `site_profile_runs`: one row per build attempt, read or not: `id`, `clerk_user_id` (cascade), `domain`, `created_at`. Counts against the daily limit.

Auth tables (`device_sessions`, `desktop_auth_codes`) are owned by the auth work.

## API (Fastify, all under `/v1`, all require an authenticated user unless marked public)

- `POST /v1/searches` with `{ kind, params, limit?, checkInboxes? }` returns the search. `checkInboxes` (default false) checks all of its role inboxes, not only the one fallback inbox a company with no valid personal address gets (pipeline step 4). Kind `domains` takes `params: { items, country? }`. While Brave is paused it is refused only when the list holds a name. Kind `icp` takes `params: { description, product?, countries?, locations? }` and is refused while Brave is paused.
- `GET /v1/searches` returns the user's searches, newest first.
- `GET /v1/searches/:id` returns one search with counters.
- `POST /v1/searches/:id/cancel`
- `PATCH /v1/searches/:id` with `{ ongoing?, checkInboxes? }`, at least one. `ongoing` switches daily rounds on or off (see "Describe your customer"). Only `icp` searches: other kinds answer 400 `ongoing_not_supported` and nothing changes. The API defaults `ongoing` to false; the web app and the desktop app switch it on for the `icp` searches they start. `checkInboxes` works on every kind: on sets `searches.check_inboxes`, clears `skipped = 'role_inbox'` on the search's unchecked role inboxes at companies with no valid personal address (the policy would skip the others again at once) and queues a verify job at priority -10 for every unchecked role inbox with no queued one (so switching on again recovers a check that got lost), pipeline step 4. The valid ones show up as they settle and only those are charged, like any verified email; off only stops future checks. Switching on is refused on a canceled search (400 `search_canceled`) and once the allowance is used up (403 `quota_exceeded`, with `billingUrl`). Both the switch and the worker's check decision lock the search row before the address, and the decision writes a `role_inbox` skip only while the switch is still off, so a skip never lands from a stale read. `Search.inboxesSkipped` counts what switching on would check and `inboxesPending` what is still to settle; `Company` carries the same two counts. The company list and the CSV still hide every unchecked address. The apps offer it as "Check shared inboxes for this search" under the Shared inboxes pill, with how many it checks, that only valid ones count and how many verified emails are left (a warning when that is fewer), and next to a company with no named person that has a skipped inbox.
- `POST /v1/searches/:id/more` with `{ kind, params, limit? }` (the search's own kind, else 400 `kind_mismatch`) runs an ended search again into the same list (pipeline step 6). 409 `search_running` while it runs; quota and Brave pause as for a new search.
- `DELETE /v1/searches/:id` deletes it with its companies and emails.
- `GET /v1/searches/:id/companies?cursor=&verification=&kind=&q=` returns companies with their emails, paginated.
- `GET /v1/searches/:id/export.csv` returns one row per email: company, domain, website, email, kind, verification, source_url, location, phone, opener (the company's drafted line when it is `done`, else blank).
- `POST /v1/searches/:id/openers` with `{ companyIds?, redo? }` queues openers and returns 202 `{ queued, skipped }`: see "Openers".
- `GET /v1/me` returns user, plan and usage for this period, how the request authenticated (`via`), the account's origin (`account`) and `billingUrl`. `?sync=1` re-reads the plan from Clerk Billing first.
- `GET /v1/plans` (public) returns the plan ladder.
- `GET /v1/site-profile`, `POST /v1/site-profile` with `{ website }`, `PATCH /v1/site-profile` with any profile fields, `DELETE /v1/site-profile` (204): see "Site profile".

## API and agents

Everything the desktop app does is open to scripts and AI agents. One catalog, `packages/shared/src/catalog.ts`, lists every endpoint (`ENDPOINTS`, with its zod schemas), every error code (`ERROR_CODES`) and every MCP tool (`MCP_TOOLS`). The server builds `GET /v1/openapi.json` and the MCP tool list from it, the site renders `/docs`, `/llms.txt` and `/agents.md` from it, and a test fails when a documented route does not exist.

**Credentials.** Every `/v1` route that needs a user accepts any of: the desktop device token (`nvk_dt_`), an API key (`nvk_sk_`), a Clerk session JWT (the site) or a Clerk OAuth access token (MCP clients). Code: `apps/server/src/api/auth.ts`.

**API keys.** `nvk_sk_` plus 32 random bytes, stored as a sha256 hash with a short display prefix. Made from the desktop Account screen or `POST /v1/api-keys` (any credential, so an agent can rotate its own), shown once, at most 20 live per account, revoked with `DELETE`. Keys have full access to the account; there are no scopes. Code: `apps/server/src/auth/api-keys.ts`.

**Agent sign-up.** `POST /v1/agents/signup` with `{ email, agentName? }` creates an account with no human in the loop (`apps/server/src/agents/signup.ts`):

1. Refuse with 422 `email_not_accepted` a disposable domain, an opted-out address (`suppressions`) or a domain without MX or A records. Refuse with 429 `rate_limited` past 3 attempts per IP an hour, 10 per email domain a day (100 for webmail domains such as gmail.com) or 300 a day overall. Attempts count, not only successes, so the 409 cannot be used to enumerate accounts.
2. 409 `account_exists` when Clerk already has the address.
3. Create the Clerk user with the address `reserved` (unverified, but nobody else can take it), no password and legal checks skipped. Insert `accounts` with `created_by = 'agent'`, `claimed_at = null`, and an API key with `origin = 'agent_signup'`. If the database step fails, the Clerk user is deleted again.
4. Mail the owner one email through Day3 (`CLAIM_EMAIL_FROM`) with a Clerk sign-in ticket in the fragment of `{SITE_URL}/claim#ticket=...`, valid 30 days. A failed email does not fail the sign-up; the response says `claimEmailSent: false`.
5. Return 201 with the key, `apiBase`, `mcpUrl`, `docsUrl` and `nextSteps`.

The account is on the free plan like any other. Unclaimed, its keys work for 7 days (`UNCLAIMED_ACTIVE_DAYS`), then answer 403 `claim_required`; the worker deletes it with its Clerk user after 30 days (`UNCLAIMED_DELETE_DAYS`, `apps/server/src/agents/purge.ts`).

**Claiming.** The site's `/claim` page redeems the ticket with Clerk, reads the account with `GET /v1/agents/claim` (the one signed-in read that claims nothing), then calls `POST /v1/agents/claim` with `{ acceptTerms: true, keepAgentKeys }`, which sets `claimed_at` and keeps or revokes the agent's key. A person who signs in any other way (the site or the desktop app) proves they own the address too: the first such request claims the account and revokes the agent's sign-up key (`Accounts.humanSignedIn`). So an agent that signed up with someone else's address loses access as soon as the owner shows up, and the owner never inherits a key they did not choose to keep.

**MCP.** `POST /mcp` on the API, Streamable HTTP, stateless, JSON responses; GET and DELETE answer 405 (`apps/server/src/api/routes/mcp.ts`, `@modelcontextprotocol/sdk`). Each tool runs the matching REST route in process (`app.inject`) with the caller's own `Authorization` header, so MCP and REST share auth, quotas and shapes. The desktop app serves the same tools locally (see "Local MCP" under Desktop screens). Tools: `get_account`, `start_search` (every client kind, `domains` with `items`), `wait_for_search` (polls up to 50 seconds), `get_search`, `list_searches`, `get_leads`, `export_csv`, `draft_openers`, `set_search_ongoing`, `set_check_inboxes` (`PATCH /v1/searches/:id` with `checkInboxes`; `start_search` takes `checkInboxes` too), `cancel_search`, `delete_search`. The server sends `MCP_INSTRUCTIONS` at `initialize`, including the EU consent caveat.

MCP auth is an API key in the bearer header, or OAuth with Clerk as the authorization server: a 401 carries `WWW-Authenticate: Bearer resource_metadata=...`, the protected resource metadata names the Clerk issuer (decoded from `CLERK_PUBLISHABLE_KEY`), and the client registers itself with Clerk (client ID metadata documents or dynamic client registration) and sends the person through Clerk's sign-in, where they can also sign up. OAuth tokens are verified with the Clerk Backend API and cached for a minute.

## Drops

Fresh leads, not a static list. The worker collects new launches around the clock, and a drop turns the new ones that match a user's filter into a search once a day.

- **Feed.** Every minute the worker runs the collectors that are due (`apps/server/src/feed/collectors.ts`) and stores what they find in `feed_items`: Show HN and Launch HN through the Algolia HN API every 30 minutes, Product Hunt every hour (needs `PRODUCT_HUNT_TOKEN`, skipped without it), Y Combinator's three newest batches from the public yc-oss mirror of the YC directory every 6 hours. A run reaches back to the last good run minus 2 hours (7 days the first time). Only what the source publishes goes in: name, website, tagline, description, tags, location. Nothing is crawled and no address is stored at collection time. Items on platform domains are skipped. A failing collector is recorded in `feed_sources` and retried at its next interval; it never stops the others. An advisory lock keeps it to one worker. `cli feed collect --prod` runs every collector now and `cli feed --prod` prints the feed per source.
- **Drops.** A drop is a name, an optional keyword (every word must appear in the item's `search_text`), a set of sources and a daily limit (default 25, at most the plan's drop limit, see "Plans"; a drop made on a bigger plan delivers what the current plan allows). At most 20 per user. The first run happens within a minute of creating the drop and reaches back 7 days (`DROP_BACKFILL_DAYS`); after that it runs every 24 hours on the same beat.
- **A run** (`runDueDrops` in `apps/server/src/feed/drops.ts`, every minute, `FOR UPDATE SKIP LOCKED` on due drops): takes the feed items after the drop's `cursor`, from its sources, matching the keyword, on a domain this drop has not delivered before, one per domain, newest first. When there are none it only moves the cursor and the next run time: no empty searches. Otherwise it inserts a search of kind `drop` (params: `dropId`, `dropName`, `keyword`, `sources`, plus the feed slice `afterId`, `untilId` and, on the first run, `since`), limit = the daily limit, with its find job, and moves the cursor to the newest item. The find step reads that slice of the feed instead of calling a source; crawl, verify, billing and retention are the same as every other search. Items past the limit are skipped, so a drop always delivers the freshest launches. A run while the user's allowance is used up creates nothing and leaves the cursor, so those launches wait for the next run.
- **Edits** apply from the next run. "Check now" (`POST /v1/drops/:id/run`) moves the next run to now. Deleting a drop keeps the searches it made.

## Webhooks

Leads pushed to the user's own URL the moment they are ready, so a drop can feed a CRM, Zapier, Make or Clay without anyone opening the app. Code in `apps/server/src/webhooks/`, schemas in `packages/shared/src/webhooks.ts`.

- **Endpoints.** A webhook is an HTTPS URL, the events it wants, and which searches it covers: `scope` `all` (every search, drops included) or `drops` (only searches a drop made), optionally narrowed to one `dropId`. At most 10 per account (`WEBHOOKS_MAX`). Deleting a drop deletes the webhooks narrowed to it, so their scope never widens on its own. `GET /v1/webhooks`, `POST /v1/webhooks` with `{ url, events, scope?, dropId? }` (409 `too_many_webhooks`), `PATCH /v1/webhooks/:id` with any of those plus `enabled`, `DELETE /v1/webhooks/:id`, `POST /v1/webhooks/:id/test`, `GET /v1/webhooks/:id/deliveries` (the last 50).
- **Events.** `lead.ready`: a company with at least one valid address, sent once its checks have settled: no address left unchecked, or the search ended (done, or failed with `quota_exceeded`, which leaves some unchecked). Once per company per webhook. `data` is `{ search: { id, kind, dropId, dropName }, company }`, where `company` has the shape of `GET /v1/searches/:id/companies`, with every checked address. `search.finished`: a search reached `done` or `failed`; `data` is `{ search }` with its counters. Canceling sends nothing. `ping`: only from the test route.
- **Payload.** `POST` with `{ type, timestamp, data }` as JSON. Headers follow Standard Webhooks (standardwebhooks.com), so its libraries verify them: `webhook-id` (the delivery id, the same on every retry; dedupe on it), `webhook-timestamp` (unix seconds) and `webhook-signature` (`v1,` plus base64 HMAC SHA-256 of `{id}.{timestamp}.{body}`, keyed with the base64 part of the secret). The secret is `whsec_` plus 24 random bytes in base64, returned once by `POST /v1/webhooks`. To rotate, make a new webhook and delete the old.
- **Delivery.** The worker sends due deliveries every 2 seconds (`FOR UPDATE SKIP LOCKED`, 20 at once, again while batches come back full). A 2xx within 10 seconds is success; redirects are not followed. Retries after 5 seconds, 5 minutes, 30 minutes, 2 hours, 5 hours, 10 hours and 10 hours, then the delivery fails. A webhook whose delivery fails for good with no success since that delivery was created (a day of failures) is disabled with `disabledReason: 'failing'`; the user turns it on again. Disabling or deleting a webhook drops its pending deliveries.
- **Built when sent.** A delivery row holds only the event and the ids it is about. The payload is built from the current data at each attempt, so a deleted search, an opt-out or an expired search drops the delivery (`skipped`) instead of sending addresses we no longer hold. No address is stored outside `emails`.
- **Safety.** Only `https` URLs on a public address: the host is resolved at create, update and every send, and the request connects to the address that passed. Loopback, private, link local, CGNAT, multicast and reserved ranges (IPv4 and IPv6, mapped addresses included) answer 422 `webhook_url_not_allowed`. `WEBHOOK_ALLOW_PRIVATE=true` lifts that and allows `http` for local development only.
- **Test.** `POST /v1/webhooks/:id/test` sends a signed `ping` from the API at once and returns `{ ok, status, error, durationMs }`. It is not stored.

## Plans

One product for everyone. Every feature is on every plan; a plan is only a monthly allowance of verified emails. The ladder lives in `packages/shared/src/plans.ts` and is shared by the server, the site and the desktop app:

| Plan key (Clerk slug) | Verified emails a month | USD a month | Companies a search | Companies a drop a day |
|---|---|---|---|---|
| `free` | 50 | 0 | 1,000 | 200 |
| `emails_1000` | 1,000 | 9 | 2,500 | 250 |
| `emails_2500` | 2,500 | 19 | 5,000 | 500 |
| `emails_10000` | 10,000 | 49 | 10,000 | 1,000 |
| `emails_25000` | 25,000 | 99 | 20,000 | 2,500 |
| `emails_60000` | 60,000 | 199 | 25,000 | 5,000 |

- The search and drop limits are not a price lever, they keep one job a sane size. They grow with the allowance so a paying user can spend it in a few searches (a search aims for about 30% of its companies as verified emails), and stop at 25,000 (`SEARCH_LIMIT_MAX`) and 5,000 (`DROP_DAILY_LIMIT_MAX`). The API holds a bigger `limit` or `dailyLimit` to the plan's without an error; `GET /v1/me` returns both as `maxSearchLimit` and `maxDropDailyLimit`.
- Capacity: verification is the ceiling, not these limits. Mail servers without IPv6 (Microsoft 365, most shared hosting) are probed over IPv4, held to `SMTP_PROBES_PER_MINUTE` (5) sessions a minute from the one VPS, of which the free tools take 1. That is about 5,760 worker sessions a day, roughly 86,000 verified emails a month for every user together, while the top plan alone allows 60,000. IPv6 sessions are far less limited. That is a good problem (it only bites once people pay), and the plan to raise it is `docs/research/smtp-throughput.md`.

- A verified email is an address whose check came back `valid`, generic or personal. Invalid, risky, catch-all and unknown results are free.
- A valid email found by a Describe your customer (`icp`) search counts as two against the allowance (`ICP_EMAIL_WEIGHT`, `emailWeight(kind)` in `plans.ts`). That search pays for Claude on every company and for web search, so its leads cost more to make. Every other kind counts one. The site's pricing page, billing and the ICP forms say so in one line.
- An address the user was charged for is not charged again while its `billed_emails` row exists, which is 12 months (see "Privacy", retention).
- Crawling stores addresses for free, but an address is only returned by the API and the CSV once its check has run. A valid address that no longer fits the allowance stays unchecked and hidden.
- When the allowance is used up, the search stops with status `failed` and error `quota_exceeded`, and new searches are refused with 403 `{ error: 'quota_exceeded', billingUrl }`. No overage is ever charged. Usage resets each calendar month (UTC); nothing rolls over.
- Plans are Clerk Billing user plans. Checkout and cancel happen on the site at `/desktop/billing`, which the desktop app opens in the browser, and at `/app/billing` inside the web app (the same component). The server reads the held plan with the Clerk Backend API (`billing.getUserBillingSubscription`): on `GET /v1/me` when the stored plan is older than 5 minutes, on `?sync=1`, and on every billing webhook. Active and past due items count, a canceled item counts until its period ends, and the most generous plan wins. A slug Clerk reports that the catalog does not know is logged as an error and never drops the user to Free.
- A plan can be granted by hand: set `publicMetadata.plan` to a plan key on the user in the Clerk dashboard. It counts like an active subscription, so a paid plan above it still wins.

## Describe your customer

Kind `icp` (`apps/server/src/leads/sources/icp.ts`). The user says who they sell to in plain words; nvoke works out where those companies are, keeps pushing until the search holds `limit` companies and, past that, until it holds enough verified emails, and says what it does in `searches.stage` and `stage_note` (shown as the live progress line). A search that comes up short never just ends.

- **Plan** (`src/leads/planner.ts`). One Sonnet call (`quality`, task `plan`) turns the words into a plan stored in `searches.plan`: core queries phrased the way such companies describe themselves on their own sites (10 to 16, in the country's language where its companies use it), list page and directory queries (6 to 14, partner and agency directories of the tools such companies use among them), adjacent niches and synonyms (8 to 14), wider geography (8 to 14: more countries when the user named none, else more cities), trade and city pairs when the customer is a local business, sales job titles only when the description or the plan's segments name sales or growth teams (sales teams, SDRs, BDRs, account executives, heads of sales or growth, RevOps, outbound teams; founders or B2B companies alone are not enough), up to 4, the usual sales development, account executive and business development titles when Claude names none, fit criteria and disqualifiers. The job titles become job post queries (see "Job posts"), one per title and country, at most 8. Every query has a country. Countries the user named are never left. A retry or a later run with the same words reuses the stored plan.
- **Company index** (`src/leads/company-index.ts`, migration `1720_company_index`). Before any web search, each round asks nvoke's own index: the kept page text of every crawled domain (`domain_pages`, up to 3 pages, 12 months) and the launches in `feed_items`, each with a full text vector (`simple` and `english`, so words match in any language and English plurals match too) and a GIN index. A trigger fills the vector on every insert and text change; the rows kept before it are filled in batches of 500 by `1721_company_index_backfill`, which runs outside a transaction (a file whose first line is `-- migrate: no transaction` runs statement by statement) and builds the indexes concurrently, so neither live table is rewritten or locked for long. Anything shaped like an email address is cut out before indexing, so the index holds company data only. Each core, adjacent and wider query of the plan, and each segment, must match all its words, and any one may match. Companies come back by text rank, one per site, at most 3 per wanted company (300 at most), without the sites the search holds or turned down, suppressed domains, domains whose last crawl failed, was blocked or refused us, and domains whose country TLD is outside the plan's countries (generic TLDs pass). They get the same first look as web results, with the kept homepage's title and description in it. The note says "Checking N companies nvoke already knows". Brave pays only for what the index left short. A failing index is logged and the search goes on. Companies from it have source `index`.
- **Tiers.** Tier 1 runs the list page and directory queries first, then the core queries and the local pairs (OpenStreetMap only, with no Brave place lookups or web fallback, at most 60 companies a pair; a place the map cannot find is skipped with a note), interleaved and spread over countries so results arrive within seconds. Tier 2 widens to adjacent niches, tier 3 to wider geography, then the job post queries run, tier 4 reads result pages 2 to 4 only of queries whose last page kept at least 3 candidates, 40% of what it gave and twice the run's average of fits per page. Companies on a list page count toward the query that found the list. Job post queries run only when the plan wants them (see Plan); a stored plan's job posts are skipped otherwise. Each tier starts only while the search is short. When every tier is spent below the limit the stage is `exhausted` and the note says so plainly. Four failed queries in a row fail the find job, so it retries instead of reporting an empty plan as done. A canceled search stops at once and gets no more notes. Notes count candidates that passed the first look and were handed to the find job, which may still skip a company the search holds, and tier 4 counts those too; fit may still turn one down after the crawl.
- **List pages** (`src/leads/listicle.ts`). A result titled like a list ("Top 25 ... agencies", "The 10 best ...") or a directory category page (clutch.co, designrush, goodfirms, sortlist, agencyspotter, themanifest, upcity and a few more) is fetched with the crawler's rules and a fetch that connects only to public addresses over http(s), checked on every hop and for robots.txt (no private, loopback, link-local or metadata targets): robots.txt on every hop, one request per second per host, reading stops at 500 KB, no CAPTCHA solving, no logins. Pages are read 6 at a time, one per host, the next starting as soon as one finishes. The companies it links to (off its own site, not platforms, directories, trackers, shorteners or affiliate links, one per domain, navigation and footer skipped, directory redirects unwrapped) become candidates with the text next to the link. A list that named companies and links its next page plainly (`?page=2`, `?p=2`, `/page/2/`, on the same site with nothing else changed) is read up to 3 pages further. Titles like "B2B SaaS startups in Berlin" and "12 Belkins alternatives" count as lists too, and so do pages under `/partners`, `/agencies`, `/experts`, `/alternatives` or `/competitors` on any site (a tool's partner directory names the agencies that use it). At most 400 list pages a run, next pages included, and at most 100 MB and 12 minutes of list page reading; a host that refuses us or links to nothing but itself is not tried again in that run. Directory pages are never candidates themselves.
- **Job posts** (`src/leads/hiring.ts`). A company advertising a sales development, business development or account executive role (or a head of sales) is building an outbound team now. They run after the wider geography: a request names 15 to 20 companies, but most are larger software companies and fewer than a fifth fit. Job post queries look for a title on the public boards of the applicant tracking systems a country's companies use, in one Brave request: `"account executive" (site:jobs.lever.co OR site:job-boards.greenhouse.io OR site:boards.greenhouse.io OR site:jobs.ashbyhq.com OR site:apply.workable.com)`, with Personio first in Germany, Austria and Switzerland, Recruitee in the Netherlands and Belgium and Teamtailor in the Nordics. Any result on such a board whose title names a sales role (from any query) is mapped to the company's own site from its public board, once per board per run: Ashby's page data (`publicWebsite`), Workable's account (`apply.workable.com/api/v1/accounts/<name>`), Greenhouse's boards API (postings hosted on the company's careers page), else the board page's link to the company (a logo, home page or imprint link, the name matching the board), else a guess from the board's name (`.com`, `.io`, `.ai`) kept only when that homepage links back to the board, or when the name has at least 6 letters, is exactly the domain's label and the homepage title names it. A guessed site is marked in the fit line and caps the job post's weight at 74. A careers subdomain stands for the company's site. Fetched with the list page rules (robots.txt on every hop, the per host rate, no logins, no CAPTCHA solving), 8 boards at a time. The candidate has source `hiring`, the posting as `sourceRef`, "Hiring: <role>" as its title and a line for fit scoring with the role, the other open sales roles and the number of open roles on the board (60 or more reads as a large company). A board that does not say and a guess that is not confirmed drop the posting.
- **Fit** (`src/leads/fit.ts`, migration `1770_fit_after_crawl`). Platforms, webmail, directories, job boards and applicant tracking system hosts, review and data sites, public bodies and `jobs.`, `news.` or `blog.` hosts are dropped before any call. Haiku (`bulk`, task `fit`) scores 0 to 100 against the description, the product and the plan's criteria, twice at most. The first look reads what the search found for free: the name, the address and the search result's title and snippet (or the list page's line, or the homepage title and description the index kept), 100 to a call, with no reasons, and drops only what scores below 40 (`GATE_FLOOR`, "not a fit"); no homepage is read before the crawl. The rest is crawled. A company whose crawl found someone to check (`needsFit`, see pipeline step 3) waits for the fit job: crawled companies are gathered per search and scored 30 to a call (`FIT_BATCH`) once 30 wait or 15 seconds after the first (`queueFit`, `FIT_WAIT_MS`), from the homepage title, description and text the crawl kept (`domain_pages`) and how the search found it (a job post for a sales role, a list page). At 60 or more (`FIT_THRESHOLD`) it is kept with `fit` and `fit_reason`, and its checks and people job are queued. Below, it is deleted with its addresses and people before anything was checked or charged, its site joins the plan's turned down sites, and the search's counts drop back. A check that runs while its company waits is dropped and queued again when the company is kept. A company with nobody to check costs no second call and keeps the first look's score. For customers named by a role (founders of B2B companies, small sales teams, SDRs) a small B2B company needs outbound evidence to fit: a current job post for a sales role scores 75 to 90 when the company is not large, other evidence (a book a demo homepage with a sales team, an outbound tool it names) 60 to 79, and a B2B company with none 45 to 59. Agencies, freelancers and consultancies are judged by what they do. The candidates sit in a delimited block the model is told to treat as untrusted data. Verdicts are matched by domain: the first answer per asked domain wins, others are dropped. A failed call is tried again and split down to single candidates; what still has no verdict scores 0 and is dropped, without joining the turned down sites. When Claude cannot be asked at all (no key, budget spent) Brave results go on unscored, list page links are left out, crawled companies are kept unscored, and the note says so; a fit job that runs out of attempts keeps its companies unscored too.
- **Brave budget.** One run reads at most `ICP_BRAVE_BUDGET` paid pages of web results (default 120; cache hits do not count). A page counts once however many requests its provider billed for it (Serper asks twice for a page of 20), and so do the ongoing budgets (`ICP_DAILY_BRAVE_BUDGET`, `ONGOING_DAILY_BRAVE_BUDGET`); `searches.source_requests` still counts every paid request. Past it the note says so, no paid tier starts, and the list pages and places already found are finished.
- **Never short** (`src/leads/ongoing.ts`). A search aims for verified emails, not companies: 30% of the limit the user asked for, at least 100 (`VERIFIED_TARGET`; verified means `emails.verification = 'valid'` for the search), never more than the account's allowance can still take: the verified count plus what is left of this month's allowance, each email of the search counting as two (`allowanceRoom`). With room for none, no round starts and the search ends with the allowance note. When its last job finishes short of that, `maybeFinishSearch` holds it `running` with stage `escalate` instead of ending it; the worker also holds it early once its find, crawls, fit and checks are done (no verify job queued, running or deferred, no company waiting for fit) and what is left cannot close the gap: the verified count plus the unchecked addresses at the share of checks that came back valid so far (every unchecked address while fewer than 20 came back), plus one per people job still queued or company with named people waiting for fit (`projectVerified`). The addresses of a company waiting for fit count as checks to come (`queuedChecks` in `src/worker/queue.ts`, at least one per such company). Addresses the policy will leave unchecked (role inboxes with inbox checks off, off-target people, and unnamed and untitled addresses of a company that already has what they wait for) do not count. So the next round starts within a tick or two and does not wait for paced people probes. No round starts while the search has checks queued or deferred; a held search that has some when claimed goes back to running ("Checking N addresses before looking further") and is judged again when its last job ends. Every 15 seconds the worker (and `cli search` and `pnpm eval`, which run the same loop) claims held searches (stage `replan`, with a claim time and attempt count in the plan, so a round a stopped worker or an unexpected error dropped is claimed again after 10, 20, then 40 minutes, and after 3 attempts the search ends saying planning failed) and asks the planner for a fresh round (`replan` in `planner.ts`, Sonnet, task `replan`): new adjacent niches, countries the search has not used (only when the user named none) or new cities in its countries, more list page and directory queries (two at each turn of the round's query budget), and new local pairs, given every query earlier plans ran (kept in `plan.ran`, at most 800), so nothing repeats. The round is stored as the plan (same key, `round` counts up) and runs as another run into the same list: `trigger: 'escalate'`, the user's latest limit as new companies, a find job, and the crawls and checks a quota stop dropped are queued again. Its note says what it does with counts from the database ("Found 140 verified so far. Looking in 9 more countries, 6 new niches and 4 more list page searches"). At most 3 fresh rounds in 24 hours per search (`MAX_ESCALATIONS_PER_DAY`), each within `ICP_BRAVE_BUDGET`. Cancel and failure write an honest last note too ("Stopped", "Stopped by an error", "This month’s allowance is used up") instead of the step the search was on. A search ends `done` with a plain final note when it reaches the target, used its 3 rounds in the last 24 hours, the account's allowance is used up, Claude is out of reach, or the planner has nothing new ("nvoke has run every search it could think of for this customer. Describe your customer more broadly or add countries to find more").
- **Ongoing.** An `icp` search with `ongoing` on runs one fresh round a day (`trigger: 'ongoing'`) at the time of day (UTC) it was created, when it ended before that time came round, so rounds do not drift later and new leads arrive over days. A daily round does not chain further rounds and its final note says what it added ("Added 12 verified emails in this daily round, 152 in all. Next round tomorrow"). Each daily round may make `ICP_DAILY_BRAVE_BUDGET` paid Brave requests (default 40) and all daily rounds together `ONGOING_DAILY_BRAVE_BUDGET` a UTC day (default 250). The round reserves its budget in `ongoing_budget` (one row per UTC day, an atomic add under the cap) before Claude plans it, gives it back when it does not start, and counts against the day it was reserved on even when it runs past midnight. The plan carries the reservation (`plan.braveBudget`) and the icp adapter holds the run to it. Searches waiting longest go first; the rest wait for the next day; a round under 4 requests is not started. Ended searches of any status are picked up (done, failed, or canceled and switched on again); a cancel switches ongoing off. While the account's allowance is used up the search stays ended with stage `paused` ("Paused until your allowance renews") and resumes when it renews. Switching ongoing off ends the pause note.
- **Cost.** Without `OPENROUTER_API_KEY` or `BRAVE_SEARCH_API_KEY` the kind fails with `source_not_configured`. A plan is about 2 US cents, a fit call about a tenth of a cent: one first look call per 100 candidates and one second look call per 30 crawled companies with someone to check. A real run for nvoke's own customers (limit 150) took 17 to 24 Brave requests and under 60 seconds.

## Source costs

Brave Search bills every request, while users pay only for valid emails. A web search that finds nothing still costs requests, so the find job keeps that cost down:

- **Stop early.** The adapter fetches one page (20 results) at a time and the find job stops pulling as soon as the search has `limit` companies, so a search never fetches pages it does not use. At most 10 pages per search.
- **Paid web search providers.** Web search has a primary paid provider (`WEB_SEARCH_PROVIDER`, `brave` by default, or `serper` for Google results from serper.dev) and an optional paid fallback (`WEB_SEARCH_FALLBACK`). The fallback answers when the primary refuses us (key, credit or quota), fails, is paused in `source_pauses`, or is past its monthly budget; the free search (Mwmbl, `FREE_SEARCH`) stays the last fallback behind both, and searches are refused as paused only when every configured provider is. Without a fallback and with Brave as primary, Brave answers alone, as before. A page is always 20 results: one Brave request, or two Serper requests of 10. Both providers share `web_search_cache` under the same query, country and page keys, with the same retention. Each paid request still counts in `searches.source_requests`; with Serper configured, each provider's requests are also counted per UTC month in `web_search_usage`, priced at `BRAVE_COST_PER_1000_USD` or `SERPER_COST_PER_1000_USD`, and alerted at 80% and 100% of `BRAVE_MONTHLY_BUDGET_USD` or `SERPER_MONTHLY_BUDGET_USD`, naming the provider. A refusing provider is paused under its own name (`nv sources resume serper`).
- **Cache.** Every page is stored in `web_search_cache` by normalized query (trimmed, lowercased, single spaced), country and page, and reused by any search for 7 days (`RETENTION.webSearchCacheDays`). A cache read or write that fails never fails the search.
- **Rate.** `BRAVE_REQUESTS_PER_SECOND` (default 1, the free plan) sets the shared rate limit, with a tenth of headroom. `web`, `domains`, `local` and `icp` searches share one client, so one limit.
- **Refusals.** A 429 whose spent window resets within 5 seconds is waited out (3 tries). A 429 for a long window (monthly quota, the usage limit set in the Brave dashboard) and any 401, 402 or 403 raise `SourceUnavailableError`: Brave is paused in `source_pauses` for 10 minutes, the operator gets an alert and the free search below answers in its place for the rest of the pause (pages Brave answered before still come from the cache). Only when the free search is off or refuses us too does the search fail with `source_unavailable` (companies already found keep crawling). While Brave is paused and the free search is off or paused too (`free_search` in `source_pauses`), `POST /v1/searches` refuses web searches with 503 `source_unavailable` and the desktop says web search is paused on our side. When the pause runs out the next web search tries Brave again, so it recovers on its own once the limit is raised. `cli sources resume brave --prod` ends it at once.
- **Free search** (`src/leads/sources/free-search.ts`, `FREE_SEARCH`). Mwmbl's public search API (`api.mwmbl.org`, no account) behind the Brave client's interface, so `web`, `domains`, `local` and `icp` use it unchanged. `fallback` (default; the owner accepted Mwmbl's terms, whose data licence is CC BY-NC-SA, on 2026-10-18) uses it when Brave refuses us, is paused or has no key; `off` is Brave alone; `first` asks it before Brave and pays Brave only when it finds nothing. Brave operators (`site:`, `OR`, quotes, `-word`) are dropped and results are held to the `site:` hosts; the country's English name joins the words and, when that finds nothing, the query is tried once without it (or without its last word). One page holds all its results (up to about 60). One request every `FREE_SEARCH_INTERVAL_MS` (default 3 seconds) as `nvokebot`, pages cached in `web_search_cache` under the country key `mwmbl:<country>` and free on reuse; an empty answer is kept for its UTC day only (`mwmbl:<country>:empty:<date>`). Its requests are never reported as `source_requests` or `source_cache_hits`, so Brave cost stays honest. A 403, 429 or 503, or a body that is not JSON and looks like a challenge page, stops it for 30 minutes (`free_search` in `source_pauses`) and is never worked around; a timeout or server error skips that query, and five in a row count as a refusal. While it answers for Brave the stage is `fallback` and the note says so ("Our main web search is unavailable right now, so nvoke is searching with Mwmbl, a free search engine. Expect fewer results"). Its index is small: good for common English phrases, thin or empty for local and long queries. Tried and left out on 2026-10-18: DuckDuckGo's HTML endpoint (a puzzle challenge for an honest user agent, from the dev machine and the VPS), Mojeek, Bing, Yahoo, Ecosia, Qwant, Startpage and Brave's own search pages (robots.txt disallows them), Yep (Cloudflare block), Marginalia (the shared public key is for experiments and spent daily; other keys are non-commercial or paid).
- **Alerts.** Operator alerts are emailed through the Day3 API (`DAY3_API_KEY`, `ALERT_EMAIL_TO`, `ALERT_EMAIL_FROM`), each key at most once an hour (`alerts_sent`). Without a key they are only logged. Alerts: a source refusing us, and Brave spend this calendar month passing 80% and 100% of `BRAVE_MONTHLY_BUDGET_USD` (requests counted in `source_requests` times `BRAVE_COST_PER_1000_USD`). `cli alert test --prod` sends a test.
- **Free name lookup.** Before a `domains` search pays for a company name, and before a `local` search pays for a place without a website, the name is tried on three free routes (`src/leads/sources/resolve-name.ts`), and the paid search is asked only when none is sure. Known: a company of the same name (legal words such as ApS and Inc ignored) that a past search found and the crawl reached, when OpenStreetMap listed its website (not a place whose website a lookup found) or its domain holds the name, and for a place when its address names the place's town; rows that disagree resolve to the one under the country's TLD, else to nothing. Guess: domains made from the name, run together and hyphenated, under the country's TLD first and then .com, .net, .io, .co and .org, at most 6 DNS lookups and 2 homepage fetches per name, fetched like the crawl (robots.txt, one request per second per host, `nvokebot`). A guess counts when its homepage is not parked or for sale, does not land on a platform or a parking host, and carries the name as its brand (a title part, `og:site_name`, a logo, the copyright line; a one word name must be a title part of its own), and for a place when the page names the town. Names of only generic words or under 4 letters are not guessed. Wikidata: the official website (P856) of the one item whose label is the name, only when the name's distinctive words run to 6 letters or more, never for people, bands or works, and only when the website holds the name; one request a second, paused 10 minutes after a refusal. Names a free route found are stored with source `known`, `guess` or `wikidata`, cost nothing, and do not count toward `MAX_PLACE_LOOKUPS`. Places keep source `osm`, and a place whose website a lookup found (free or Brave) carries the route in its `source_ref` (`node/42#guess`), so the known route never takes it as the map's word. A `local` search tries at most 50 places on the free routes (`MAX_FREE_PLACE_LOOKUPS`) and starts none after 2 minutes (`FREE_LOOKUP_BUDGET_MS`). Each search logs how many names each route resolved, how many the paid search found and how many stayed unresolved.
- **Names.** A `domains` search pays only for names: one request each, none for domains, and none for a name looked up in the last 7 days. Its requests count toward the Brave budget like `web`.
- **Places.** A `local` search pays for places that list no website only when OpenStreetMap's places with a website fall short of the limit: one request per place, at most 50 per search (25 US cents), none for a place looked up in the last 7 days. They count toward the Brave budget like `web`.
- **Measure.** Each search counts its paid requests (`source_requests`) and pages served from the cache (`source_cache_hits`). `cli stats --days 30 --prod` on the VPS prints them per kind next to valid emails, with valid emails per paid request.

## Claude

Features that need judgment on text (the site profile, openers) call Claude through OpenRouter (`OPENROUTER_API_KEY`) and `apps/server/src/ai`, never the HTTP API directly.

- **Models.** `MODELS` in `src/ai/models.ts`: `bulk` is `anthropic/claude-haiku-5.5` for many small calls, `quality` is `anthropic/claude-sonnet-5.5` where the answer matters (the plan of a Describe your customer search). The cost is what OpenRouter reports per call, with prices next to the models as the fallback.
- **Structured output.** `createAi(...).structured({ userId, task, tier, system, prompt, schema, toolName, toolDescription })` asks for a JSON answer (structured outputs) whose schema comes from the zod schema, trimmed to shape, types and enums, and validates the answer with the full zod schema. Errors are `AiError` with a code: `unavailable` (no `OPENROUTER_API_KEY`), `budget_exceeded`, `refusal`, `no_output`, `invalid_output`.
- **Cost.** Every call is a row in `ai_usage` (user, task, model, tokens, `cost_usd`, no prompt or response text) and a log line with the user id. Before a call, the account's spend this calendar month (UTC) is checked against its budget: `AI_MONTHLY_BUDGET_PRICE_SHARE` (default 0.25) of the plan's price, never below `AI_MONTHLY_BUDGET_FLOOR_USD` (default 1). The check is not locked, so calls running at once may overshoot by their own cost.

## Site profile

Start from your website: the user pastes their own site and nvoke plans the searches. Code in `apps/server/src/profile`, route in `src/api/routes/site-profile.ts`, schemas in `packages/shared/src/site-profile.ts`.

- **Read.** `POST /v1/site-profile` with `{ website }` (a domain or URL) reads the homepage and up to 4 pages that describe the business, picked from its links: pricing, services, about, product, customers, one of each (`readSite`). Same fetcher and rules as the email crawl: robots.txt on every hop, one request per second per host, 2 MB, no new page after 20 seconds, and the whole build stops after 60 seconds or when the caller hangs up. Every connection, redirects and robots.txt included, is pinned to addresses the webhook URL guard checked (`src/profile/guarded-fetch.ts`), so private addresses and DNS rebinding are refused. Visible text is kept, 6,000 characters a page and 20,000 in all; nav, footer, forms and scripts are dropped.
- **Pictures.** `icon` and `image` on the profile prove the site was read. The icon is the first of apple-touch-icon, an SVG icon, the largest declared icon and `/favicon.ico` that loads; the image is the site's `og:image` (or `twitter:image`). Both are https URLs on the site, checked through the guarded fetch to answer 200 with an image under 3 MB, and hotlinked by the screens. A site without a share image that loads gets a screenshot of its homepage instead (`src/profile/site-shot.ts`, when `SITE_SHOTS` is on): headless Chromium (playwright-core) at 1280 by 800, JPEG, one at a time with at most one waiting, 15 seconds in all. Chromium never reaches the network itself: every request is fulfilled through the guarded fetch, non-GET requests and WebSockets are refused, service workers blocked, 600 requests and 40 MB at most. The JPEG is stored in `site_shots`, one per account, replaced on every build, and served without auth at `{PUBLIC_API_URL}/site-shots/<token>.jpg` (cached for a year; a new build means a new token). Pictures are found while Claude reads; no picture never fails a build.
- **Unreadable.** 422 `site_unreadable` with `detail`: `unreachable`, `blocked` (robots.txt), `refused` (401, 403, 429, 503 or a bot challenge), `js_only`, `empty` (under 200 characters of text) or `not_allowed` (a private or local address). Claude is not called.
- **Profile.** Claude (`bulk` tier for now, Haiku, to try before paying for Sonnet; task `site-profile`, through `src/ai`) answers with `name`, `summary`, `offer`, `audience`, `proofPoints`, `voice` (the site's own words, in its language), `language` and `country`, using only what the pages say. Stored in `site_profiles`, one per account, replaced on every build. `PATCH` edits any field and keeps the suggestions. `DELETE` removes the profile and its screenshot (204, 404 when there is none); searches started from it stay, and openers write about the company only. Openers read the profile.
- **Suggestions.** 3 to 6 searches in the real kinds (local niche and location, web keyword and country, launches, domains with named companies), each with one line on why. Each is checked against `CreateSearchRequest` and dropped when it does not fit, so `suggestion.search` is a `POST /v1/searches` body as is, `limit` 100 (domains: the list). When none fits, the build is `ai_unavailable` and the old profile stays.
- **Free, limited.** Building counts no verified emails. 10 attempts a day per account (`site_profile_runs`, read or not, inserted before counting so parallel requests cannot pass together), then 429 `rate_limited`. A Claude failure or a spent monthly Claude budget is 503 `ai_unavailable` and keeps the old profile.
- **Screens.** New search in the web app and the desktop opens on "Start from your website" (step one), or straight on the suggestions once a profile exists; each suggestion starts its search in one click; "Set up a search by hand" opens the manual form. A first run (no searches) leads there, and says so when a read is running or a profile is already planned. A read in progress has Cancel (and Escape), which hangs up so the server stops reading, and goes back to the field or the profile it would have replaced. Leaving New search mid-read keeps it running: coming back shows its phases where they were, or what went wrong. Remove, on the profile and in the website row's menu on Searches, deletes it after a confirm and goes to Searches.

## Openers

One drafted first line per company, for the user to copy or export. nvoke never sends. Code in `apps/server/src/openers`, route in `src/api/routes/leads.ts`, schemas (`Opener`, `DraftOpenersRequest`, `DraftOpenersResponse`) in `packages/shared/src/leads.ts`.

- **Ask.** `POST /v1/searches/:id/openers` with `companyIds` (some companies) or none (the whole search). Only companies with at least one valid, unsuppressed address qualify, so the work follows the verified emails the plan pays for. Without `redo`, a company with an opener (`done`, `none`) or one `queued` is skipped; `failed` is asked again. With `redo`, everything but `queued` is drafted again. Returns 202 `{ queued, skipped }` (skipped: asked for but not queued). 503 `ai_unavailable` when Claude is not configured or the account spent its monthly Claude budget (`src/ai/usage.ts`); 404 for another user's search. The companies turn `queued` at once and the route queues one `opener` job per 8 (`OPENER_BATCH`), without a search id, so openers never hold a running search open and cancel leaves them be.
- **Draft.** The worker's `opener` job (`runOpener`, a quarter of the worker's slots, 3 minutes) reads the companies' kept page text (`domain_pages`). A company without kept text (a cached crawl from before openers, or a site only the desktop could read) is `none` without a call. The rest go to Claude in one structured call (`bulk` tier, Haiku, task `opener`) with the account's site profile (name, what they do, offer, audience, proof) as the sender when there is one, else "write about the company only". Each company is keyed `c1`, `c2` ... in the prompt.
- **No invented facts.** Claude answers per key with `line`, `quote` (the words on the page the line rests on, copied exactly) and `sourceUrl`. The line is kept only when the quote, matched without case, spacing or typographic quotes, is on that page's title, description or text, the page is one of the company's, the quote is 12 to 300 characters and the line is at most 300 characters with no merge tags or placeholders (`{{...}}`, `[...]`, `<...>`, `%NAME%`, "first name"). Dashes used as punctuation become commas. Anything else is `none`. The prompt also forbids greetings, names of people, praise and claims about the sender beyond the profile, and writes in the language of the company's pages.
- **Store and show.** `done` stores the line, quote and source URL on the company row. A Claude failure (`AiError`: refusal, no or invalid output, budget spent) marks the batch `failed` at once; other errors retry the job, and a job that gives up marks its companies `failed`. `GET /v1/searches/:id/companies` returns `opener` on each company (`null` until asked), the CSV has the `opener` column, `lead.ready` webhooks carry it, and the MCP tool `draft_openers` asks for them.
- **Screens.** The web app and the desktop show the line under the company with Copy and a "from /page" link to the source (the quote on hover), "Draft openers" and "Draft openers again" in the search's menu, and refresh while any opener is `queued`. The desktop also drafts for the selected rows; the web app per row.

## Free tools

Acquisition pages on nvoke.run/tools, each backed by a public route under `/v1/tools` (`src/api/routes/tools.ts`, schemas in `packages/shared/src/tools.ts`). No sign-in; every result ends in "Start free".

- **Email verifier** (`/tools/email-verifier`, `POST /v1/tools/verify-email`). The pipeline's verifier, run in the API. Port 25 is shared with the worker on the same VPS and Hostinger throttles it past about 5 connections a minute, so the tools get their own share, `TOOLS_SMTP_PROBES_PER_MINUTE` (default 1), which the worker gives up (`workerProbesPerMinute`). On top of that a daily cap of 300 probes. Past either, or for an opted-out address, the answer comes from syntax, disposable lists and MX only and says `depth: domain` ("sign up for the full check"). Results read and write the shared `email_checks` cache (30 days, 1 day for unknown).
- **Website email extractor** (`/tools/website-email-extractor`, `POST /v1/tools/extract-emails`). One domain, the pipeline crawler at 6 pages and 25 seconds, robots.txt on every hop, every fetch refused when the host resolves to a private address. An opted-out domain is not read (`opted_out`); opted-out addresses are dropped. Answers from the shared crawl cache when it is fresh and writes a fresh crawl back to it. Anonymous users see only generic role addresses; addresses of people are a count (`hiddenPersonal`). At most 3 crawls at once and 300 a day.
- **SPF and DMARC checker** (`/tools/spf-dmarc-checker`, `POST /v1/tools/email-auth`). DNS only: MX, SPF (one record, the `all` qualifier, lookups counted through includes against the limit of 10), DMARC (policy, `rua`, `pct`) and DKIM under common selectors, each graded pass, warn or fail.
- **Limits.** Per client IP an hour: 10 verifications, 5 extractions, 30 DNS checks (429 `rate_limited`). Daily caps answer 429 `busy`. Counters are in memory in the one API process. With `TURNSTILE_SECRET_KEY` set (and `NEXT_PUBLIC_TURNSTILE_SITE_KEY` on the site) the verifier and extractor also need a Turnstile token (403 `captcha_failed`).

## Privacy

Full documents: `docs/legal/` (`lia.md` legitimate interest assessment, `dpia.md`, `ropa.md` record of processing, `article-14.md`, `lawyer-brief.md` with the open questions). Background research: `docs/research/gdpr-competitors.md`. Rights requests: `deploy/PRIVACY-RUNBOOK.md`.

- **Positioning.** nvoke is a prospecting research tool, never a "cold email" tool. In Denmark, Markedsføringsloven §10 requires prior consent for marketing email to anyone, B2B, info@ and employees included. Customers are bound to it by the terms. nvoke itself never sends email.
- **Roles and basis.** nvoke is controller for collection, classification, verification, the shared cache and the suppression list, on legitimate interest (Art 6(1)(f)). The customer is an independent controller for its own use of what it views and exports.
- **Collection.** Only addresses published on the company's own public pages, within the crawl limits in the pipeline. robots.txt honoured, no logins, no CAPTCHA solving, named user agent linking to `/bot`. No names, titles or social profiles are extracted.
- **Local render crawl.** On by default in the desktop app, off with one switch on Account, and the switch says what it does: the user's computer reads the pages over the user's connection, so the site sees the user's IP address together with the `nvokebot` user agent. It collects exactly what the server crawl would (same pages, same robots.txt, same limits, no logins, no CAPTCHAs), so it adds no new category of data, only sites our servers are refused from, cannot render, or read without finding an address. The site is told honestly who is reading, and a site that wants nvoke out blocks `nvokebot` in robots.txt, which the local crawl obeys too. What leaves the computer is addresses and source URLs, nothing else; the browsing session lives in memory and is wiped after every company. Local results stay in the user's own search and never enter the shared cache.
- **Split cache.** Only generic addresses are shared between users (`domain_emails`). Personal addresses exist only in the `emails` of the search that found them and are deleted with it.
- **Suppression.** `suppressions` is checked before storing a crawl result, before serving from the cache and before export. An opt-out or erasure (`apps/server/src/privacy/erase.ts`) suppresses first, then deletes every stored copy: `emails`, `domain_emails`, `domains`, `email_checks`, `billed_emails` and, for a domain, the companies found on it (subdomains included). Shared mailbox domains such as gmail.com cannot be suppressed as a whole from the public page. Sources: the public `/opt-out` page and API, the `/bot` page, privacy@nvoke.run, and admin (`cli privacy suppress-domain`).
- **Retention**, enforced by `purge()` in the worker (hourly):
  - `domain_emails`: deleted 12 months after `first_seen` (never reset by a new search or recrawl), and as soon as a recrawl no longer finds the address.
  - `searches` with their `companies` and `emails`: deleted 12 months after `created_at`, or earlier when the user deletes the search.
  - `email_checks`: 30 days.
  - `web_search_cache`: 7 days after `fetched_at`.
  - `feed_items`: 90 days after `discovered_at`. Erasing a domain deletes its feed items too.
  - `webhook_deliveries`: 30 days after `created_at`. They hold ids only, never addresses.
  - `billed_emails`: 12 months after `billed_at`. Finding the address again after that charges it again.
  - `domains`: dropped 12 months after `recheck_at` when no search crawled the domain again.
  - `suppressions`: forever, so an opted-out address is never collected again.
- **Desktop local copy.** The desktop app keeps a copy of what the API returns for the signed-in user (searches, companies, checked emails) in `leads.sqlite` in the app's user data folder, unencrypted and protected by the OS account like any document. It mirrors the API: each search is fetched again at least every 6 hours while the app runs and online, and the fetch replaces its companies, so an address removed by an opt-out, an erasure or retention leaves the copy on the next fetch. A search the API no longer lists (deleted, purged after 12 months, or past the newest 200) is deleted locally on the next sync, which runs every minute. Deleting a search in the app drops it locally at once. Signing out, including a sign out forced by a revoked session, deletes the file. The copy is never sent anywhere.
- **Transparency.** Article 14 notice on `/privacy` (Danish and English). No individual notification today; whether personal addresses need one is open (`docs/legal/article-14.md`).
- **Rights.** Access, erasure and objection by email to privacy@nvoke.run, handled with `cli privacy export`, `cli privacy erase` and `cli privacy suppress-domain`. Access answers name the source URL of every address.
- **Open items** (details in `docs/legal/`): Article 14 for personal addresses, §10 co-liability, SMTP probes, source terms of use, whether `billed_emails` should hold hashes instead of plain addresses, Supabase region and VPS host. Webmail addresses (gmail.com and similar) are always classified personal and never cached.
