# nvoke v1 spec

nvoke is a lead finder sold to paying customers. A native desktop app (Electron) is the main product surface; the same features are open to code and AI agents through a REST API and an MCP server (see "API and agents"). The user starts a search, the backend on our VPS finds companies, crawls their websites, extracts email addresses and checks that they can receive mail. The user browses, filters and exports the results.

## Search kinds

| kind | user gives | where companies come from |
|---|---|---|
| `local` | niche + location, e.g. "dentists" + "Copenhagen" | OpenStreetMap: Nominatim to resolve the location to a bounding box, Overpass to find matching businesses (by tag and name) that have a `website`. Free, no key. |
| `web` | keyword, optional country | Brave Search API (`BRAVE_SEARCH_API_KEY`). Take result domains, drop big platforms (social networks, marketplaces, Wikipedia, news). Paid per request, see "Source costs". |
| `launches` | optional keyword filter, time window | Product Hunt and Hacker News "Show HN" (port from `../probe/apps/worker/src/sources`). |
| `domains` | a list: domains, URLs, email addresses or company names, up to the search limit, optional country | The list itself. Domains (and the domain of an email address) go straight to the crawl, at no cost; webmail addresses are skipped. Each name costs one Brave request (the first result page, through the same cache, rate limit and refusal rules as `web`, see "Source costs"); platform and webmail domains are dropped and the result whose domain looks most like the name wins (legal words such as ApS and Inc ignored, æ ø å folded), else the first usable one of the top 3, else the name is skipped. `splitList` in `packages/shared/src/lists.ts` turns pasted text into items. |
| `drop` | nothing: a drop makes it (see "Drops") | The feed the worker collects around the clock. |

Each source is an adapter with the same interface, so more can be added later:

```ts
interface SourceAdapter<P> {
  kind: SearchKind
  find(params: P, ctx: { limit: number; signal: AbortSignal; log: Logger }): AsyncIterable<FoundCompany>
}
type FoundCompany = { name: string; website: string; source: string; sourceRef?: string; location?: string; phone?: string; category?: string }
```

## Pipeline per search

1. API inserts a `searches` row (`queued`) and a `find` job.
2. Worker runs the source adapter, inserts `companies` rows (deduped per search by normalized domain), and enqueues one `crawl` job per company. It stops at the search's `limit` (default 100, at most 1,000 on every plan). A `domains` search has as many as its list: the API cuts the list to `limit` when one is given and stores the length as the limit. Its find job may run 30 minutes, since names are looked up at Brave's rate.
3. `crawl`: skip the company if its domain is suppressed (see "Privacy"). Otherwise check the shared cache (`domains`): a fresh row (`recheck_at` in the future) is reused when the last crawl found no personal addresses, or when it failed or was blocked. Reuse copies the domain's cached generic addresses (`domain_emails`) into this search's `emails`, minus suppressed ones, without fetching anything. In every other case crawl again: fetch the homepage plus likely pages (contact, about, team, impressum, privacy, legal), max 8 pages and 2 MB per company. Respect robots.txt. Identify as `nvokebot/1.0 (+https://nvoke.run/bot)`. At most 1 request per second per domain and a global concurrency cap. Extract emails from text, `mailto:` links, and simple obfuscations ("name [at] domain [dot] com"). Port and extend `../probe/apps/worker/src/contact/extract.ts`. Drop image filenames, placeholder addresses (example.com, sentry, wixpress, etc.) and addresses on unrelated domains unless they are the only ones found. Classify each address `generic` (role mailbox) or `personal` (always for webmail such as gmail.com). Then drop suppressed addresses, store all remaining addresses in this search's `emails`, upsert the `domains` row (`recheck_at` 90 days after a crawl, 7 days after a failed or blocked one, `has_personal` set when personal addresses were found), upsert the generic addresses into `domain_emails` (`first_seen` never changes, `last_seen` moves to now) and delete the domain's cached addresses this crawl no longer found. Personal addresses never go into the shared cache.
4. `verify`: per email, check syntax, common freemail typos (`gmial.com` and the like, `invalid`), the disposable domain list and MX records (a domain whose MX belongs to a parking service is `invalid`), then an SMTP RCPT probe without sending (EHLO, MAIL FROM, RCPT TO, QUIT). The same session asks about two random addresses on the domain; if the server accepts either, the domain is `catch_all`. A 4xx reply (greylisting) is not cached: the verify job is queued again 10 minutes later, twice, before the address settles as `unknown`. If outbound port 25 is blocked on the VPS, fall back to MX-only and mark `verification = 'unknown'`. Cache results per address: `valid` for 7 days, so a charged address was confirmed within the week, `unknown` for 1 day, the rest for 30 days. A `valid` result is charged against the user's plan in the same transaction (see "Plans"); every other result is free.
   Cached addresses go through the same verify step and count toward the quota the same way: a user pays per valid verification, wherever the address came from.
5. When all jobs for a search are finished, the search becomes `done` (or `failed` with an error).

Everything is a row in a Postgres `jobs` table claimed with `FOR UPDATE SKIP LOCKED`. No Redis. Retries use exponential backoff, max 3 attempts. The worker handles SIGTERM cleanly. The worker also runs the retention purge (`apps/server/src/leads/retention.ts`) at start and then hourly (see "Privacy").

## Data model (Postgres, public schema, RLS enabled with no policies)

- `accounts`: `clerk_user_id` pk, `plan` (a key from `packages/shared/src/plans.ts`, default `free`), `plan_synced_at` (last read from Clerk Billing), `created_by` (`human` | `agent`), `agent_name`, `claimed_at` (null while an agent-created account is unclaimed), `created_at`. Created on first authenticated request, or by agent sign-up.
- `api_keys`: `id`, `clerk_user_id`, `name`, `key_hash` (sha256, the key is never stored), `prefix` (shown in lists), `origin` (`user` | `agent_signup`), `created_at`, `last_used_at` (written at most once a minute), `revoked_at`.
- `agent_signups`: one row per sign-up attempt for the rate limits: `ip_hash` (sha256, never the IP), `email_domain`, `clerk_user_id`, `created_at`. Kept 30 days.
- `searches`: `id` uuid, `clerk_user_id`, `kind`, `params` jsonb, `limit` int, `status` (`queued` | `running` | `done` | `failed` | `canceled`), `error`, counters (`companies_found`, `companies_crawled`, `emails_found`, `emails_valid`, and `source_requests` and `source_cache_hits` from "Source costs"), `created_at`, `started_at`, `finished_at`.
- `companies`: `id`, `search_id`, `clerk_user_id`, `name`, `domain`, `website`, `source`, `source_ref`, `location`, `phone`, `category`, `crawl_status` (`pending` | `done` | `failed` | `blocked`), `crawled_at`. Unique `(search_id, domain)`.
- `emails`: `id`, `company_id`, `search_id`, `clerk_user_id`, `address` (lowercase), `kind` (`generic` like info@/contact@, or `personal`), `source_url`, `verification` (`valid` | `invalid` | `risky` | `catch_all` | `unknown`), `checked_at`. Unique `(company_id, address)`.
- `email_checks`: cache keyed by `address`, with `verification`, `mx_host`, `checked_at`.
- `usage`: `clerk_user_id`, `period` (yyyy-mm), `emails_verified`.
- `billed_emails`: `clerk_user_id`, `address`, `period`, `billed_at`. Primary key `(clerk_user_id, address)`: every address a user was ever charged for.
- `domains`: shared crawl cache, one row per domain: `domain` pk (lowercase), `crawl_status` (`done` | `failed` | `blocked`), `crawled_at`, `has_personal` (the last crawl found personal addresses, which are not cached), `recheck_at` (after this the next search that finds the domain crawls it again).
- `domain_emails`: generic addresses only, shared across users: `domain` (fk to `domains`, cascade), `address` (lowercase), `source_url`, `first_seen` (fixed at first collection, drives retention), `last_seen`. Primary key `(domain, address)`.
- `suppressions`: opted-out addresses and domains, stored only as `hash` pk (sha256 hex of the lowercased address, or of `'domain:' || registrable domain`), `kind` (`address` | `domain`), `source` (`opt_out_page` | `email` | `bot_page` | `admin`), `created_at`. Kept forever. Code in `apps/server/src/leads/suppression.ts`.
- `web_search_cache`: Brave result pages keyed by `(query, country, page)`: `companies` jsonb (name, website, result URL only, never the raw response), `more` (Brave has a next page), `fetched_at`.
- `alerts_sent`: `key` pk, `sent_at`. When each operator alert last went out (see "Source costs").
- `source_pauses`: `source` pk (`brave`), `reason`, `paused_at`, `until`.
- `jobs`: `id`, `type` (`find` | `crawl` | `verify`), `payload` jsonb, `status`, `attempts`, `run_after`, `locked_at`, `last_error`.
- `feed_items`: launches collected for drops: `id` (identity, the drop cursor), `source`, `source_ref` (unique together), `name`, `website`, `domain`, `tagline`, `description`, `tags`, `location`, `launched_at`, `discovered_at`, `search_text` (lowercased name, tagline, description and tags). No addresses.
- `feed_sources`: one row per collector: `source` pk, `last_run_at`, `last_ok_at`, `last_error`, `last_found`, `last_added`.
- `drops`: `id`, `clerk_user_id`, `name`, `keyword`, `sources`, `daily_limit`, `enabled`, `cursor` (highest `feed_items.id` already considered), `next_run_at`, `last_delivered_at`, `created_at`. `searches.drop_id` points at the drop that made a search (set null when the drop is deleted).
- `webhooks`: `id`, `clerk_user_id`, `url`, `secret`, `events`, `scope` (`all` | `drops`), `drop_id` (cascade), `enabled`, `disabled_reason`, `last_success_at`, `last_failure_at`, `last_error`, `created_at`. See "Webhooks".
- `webhook_deliveries`: `id` (the `webhook-id` header), `webhook_id` (cascade), `event`, `search_id` (cascade), `company_id` (cascade, `lead.ready` only), `status` (`pending` | `delivered` | `failed` | `skipped`), `attempts`, `next_attempt_at`, `locked_until`, `last_status`, `last_error`, `created_at`, `delivered_at`. Unique `(webhook_id, event, search_id, company_id)`.

Auth tables (`device_sessions`, `desktop_auth_codes`) are owned by the auth work.

## API (Fastify, all under `/v1`, all require an authenticated user unless marked public)

- `POST /v1/searches` with `{ kind, params, limit? }` returns the search. Kind `domains` takes `params: { items, country? }`. While Brave is paused it is refused only when the list holds a name.
- `GET /v1/searches` returns the user's searches, newest first.
- `GET /v1/searches/:id` returns one search with counters.
- `POST /v1/searches/:id/cancel`
- `DELETE /v1/searches/:id` deletes it with its companies and emails.
- `GET /v1/searches/:id/companies?cursor=&verification=&kind=&q=` returns companies with their emails, paginated.
- `GET /v1/searches/:id/export.csv` returns one row per email: company, domain, website, email, kind, verification, source_url, location, phone.
- `GET /v1/me` returns user, plan and usage for this period, how the request authenticated (`via`), the account's origin (`account`) and `billingUrl`. `?sync=1` re-reads the plan from Clerk Billing first.
- `GET /v1/plans` (public) returns the plan ladder.
- `GET /v1/api-keys`, `POST /v1/api-keys` with `{ name }`, `DELETE /v1/api-keys/:id`: see "API and agents".
- `POST /v1/agents/signup` (public, rate limited) and `POST /v1/agents/claim` (Clerk session): see "API and agents".
- `GET /v1/openapi.json` (public): OpenAPI 3.1 for every route.

- `GET /v1/drops` returns the user's drops (with `companiesDelivered`) and per feed source whether it is collected and how many launches it brought in over the last 7 days. `POST /v1/drops` with `{ name, keyword?, sources?, dailyLimit? }` (409 `too_many_drops` past 20), `PATCH /v1/drops/:id` with any of those plus `enabled` (`keyword: null` removes it), `POST /v1/drops/:id/run`, `DELETE /v1/drops/:id`. Schemas in `packages/shared/src/drops.ts`.
- `GET /v1/webhooks`, `POST /v1/webhooks`, `PATCH /v1/webhooks/:id`, `DELETE /v1/webhooks/:id`, `POST /v1/webhooks/:id/test`, `GET /v1/webhooks/:id/deliveries`: see "Webhooks".
- `POST /v1/privacy/opt-out` (public, rate limited) with `{ email }` or `{ domain }` suppresses it at once and deletes matching data. No confirmation step. Always returns `{ ok: true }`, so it cannot be used to test whether nvoke holds an address. Schema in `packages/shared/src/privacy.ts`.

Outside `/v1`: `POST /mcp` (the MCP server), `/.well-known/oauth-protected-resource[/mcp]` and `/.well-known/oauth-authorization-server` (OAuth discovery for MCP clients), and `POST /webhooks/clerk` takes Clerk Billing events (signed with `CLERK_WEBHOOK_SIGNING_SECRET`) and re-reads the paying user's plan.

Request and response shapes live as zod schemas in `packages/shared/src/leads.ts` and are the single source of truth for server and desktop. The desktop polls `GET /v1/searches/:id` every 2 seconds while a search is running.

## API and agents

Everything the desktop app does is open to scripts and AI agents. One catalog, `packages/shared/src/catalog.ts`, lists every endpoint (`ENDPOINTS`, with its zod schemas), every error code (`ERROR_CODES`) and every MCP tool (`MCP_TOOLS`). The server builds `GET /v1/openapi.json` and the MCP tool list from it, the site renders `/docs`, `/llms.txt` and `/agents.md` from it, and a test fails when a documented route does not exist.

**Credentials.** Every `/v1` route that needs a user accepts any of: the desktop device token (`nvk_dt_`), an API key (`nvk_sk_`), a Clerk session JWT (the site) or a Clerk OAuth access token (MCP clients). Code: `apps/server/src/api/auth.ts`.

**API keys.** `nvk_sk_` plus 32 random bytes, stored as a sha256 hash with a short display prefix. Made from the desktop Account screen or `POST /v1/api-keys` (any credential, so an agent can rotate its own), shown once, at most 20 live per account, revoked with `DELETE`. Keys have full access to the account; there are no scopes. Code: `apps/server/src/auth/api-keys.ts`.

**Agent sign-up.** `POST /v1/agents/signup` with `{ email, agentName? }` creates an account with no human in the loop (`apps/server/src/agents/signup.ts`):

1. Refuse with 422 `email_not_accepted` a disposable domain, an opted-out address (`suppressions`) or a domain without MX or A records. Refuse with 429 `rate_limited` past 3 attempts per IP an hour, 10 per email domain a day (100 for webmail domains such as gmail.com) or 300 a day overall. Attempts count, not only successes, so the 409 cannot be used to enumerate accounts.
2. 409 `account_exists` when Clerk already has the address.
3. Create the Clerk user with the address `reserved` (unverified, but nobody else can take it), no password and legal checks skipped. Insert `accounts` with `created_by = 'agent'`, `claimed_at = null`, and an API key with `origin = 'agent_signup'`. If the database step fails, the Clerk user is deleted again.
4. Mail the owner one email through Day3 (`CLAIM_EMAIL_FROM`) with a Clerk sign-in ticket in the fragment of `{SITE_URL}/claim#ticket=...`, valid 30 days. A failed email does not fail the sign-up; the response says `claimEmailSent: false`.
5. Return 201 with the key, `apiBase`, `mcpUrl`, `docsUrl` and `nextSteps`.

The account is on the free plan like any other. Unclaimed, its keys work for 7 days (`UNCLAIMED_ACTIVE_DAYS`), then answer 403 `claim_required`; the worker deletes it with its Clerk user after 30 days (`UNCLAIMED_DELETE_DAYS`, `apps/server/src/agents/purge.ts`).

**Claiming.** The site's `/claim` page redeems the ticket with Clerk, reads the account with `GET /v1/agents/claim` (the one signed-in read that claims nothing), then calls `POST /v1/agents/claim` with `{ acceptTerms: true, keepAgentKeys }`, which sets `claimed_at` and keeps or revokes the agent's key. A person who signs in any other way (the site or the desktop app) proves they own the address too: the first such request claims the account and revokes the agent's sign-up key (`Accounts.humanSignedIn`). So an agent that signed up with someone else's address loses access as soon as the owner shows up, and the owner never inherits a key they did not choose to keep.

**MCP.** `POST /mcp` on the API, Streamable HTTP, stateless, JSON responses; GET and DELETE answer 405 (`apps/server/src/api/routes/mcp.ts`, `@modelcontextprotocol/sdk`). Each tool runs the matching REST route in process (`app.inject`) with the caller's own `Authorization` header, so MCP and REST share auth, quotas and shapes. The desktop app serves the same tools locally (see "Local MCP" under Desktop screens). Tools: `get_account`, `start_search` (every client kind, `domains` with `items`), `wait_for_search` (polls up to 50 seconds), `get_search`, `list_searches`, `get_leads`, `export_csv`, `cancel_search`, `delete_search`. The server sends `MCP_INSTRUCTIONS` at `initialize`, including the EU consent caveat.

MCP auth is an API key in the bearer header, or OAuth with Clerk as the authorization server: a 401 carries `WWW-Authenticate: Bearer resource_metadata=...`, the protected resource metadata names the Clerk issuer (decoded from `CLERK_PUBLISHABLE_KEY`), and the client registers itself with Clerk (client ID metadata documents or dynamic client registration) and sends the person through Clerk's sign-in, where they can also sign up. OAuth tokens are verified with the Clerk Backend API and cached for a minute.

## Drops

Fresh leads, not a static list. The worker collects new launches around the clock, and a drop turns the new ones that match a user's filter into a search once a day.

- **Feed.** Every minute the worker runs the collectors that are due (`apps/server/src/feed/collectors.ts`) and stores what they find in `feed_items`: Show HN and Launch HN through the Algolia HN API every 30 minutes, Product Hunt every hour (needs `PRODUCT_HUNT_TOKEN`, skipped without it), Y Combinator's three newest batches from the public yc-oss mirror of the YC directory every 6 hours. A run reaches back to the last good run minus 2 hours (7 days the first time). Only what the source publishes goes in: name, website, tagline, description, tags, location. Nothing is crawled and no address is stored at collection time. Items on platform domains are skipped. A failing collector is recorded in `feed_sources` and retried at its next interval; it never stops the others. An advisory lock keeps it to one worker. `cli feed collect --prod` runs every collector now and `cli feed --prod` prints the feed per source.
- **Drops.** A drop is a name, an optional keyword (every word must appear in the item's `search_text`), a set of sources and a daily limit (default 25, at most 200). At most 20 per user. The first run happens within a minute of creating the drop and reaches back 7 days (`DROP_BACKFILL_DAYS`); after that it runs every 24 hours on the same beat.
- **A run** (`runDueDrops` in `apps/server/src/feed/drops.ts`, every minute, `FOR UPDATE SKIP LOCKED` on due drops): takes the feed items after the drop's `cursor`, from its sources, matching the keyword, on a domain this drop has not delivered before, one per domain, newest first. When there are none it only moves the cursor and the next run time: no empty searches. Otherwise it inserts a search of kind `drop` (params: `dropId`, `dropName`, `keyword`, `sources`, plus the feed slice `afterId`, `untilId` and, on the first run, `since`), limit = the daily limit, with its find job, and moves the cursor to the newest item. The find step reads that slice of the feed instead of calling a source; crawl, verify, billing and retention are the same as every other search. Items past the limit are skipped, so a drop always delivers the freshest launches. A run while the user's allowance is used up creates nothing and leaves the cursor, so those launches wait for the next run.
- **Edits** apply from the next run. "Check now" (`POST /v1/drops/:id/run`) moves the next run to now. Deleting a drop keeps the searches it made.

## Webhooks

Leads pushed to the user's own URL the moment they are ready, so a drop can feed a CRM, Zapier, Make or Clay without anyone opening the app. Code in `apps/server/src/webhooks/`, schemas in `packages/shared/src/webhooks.ts`.

- **Endpoints.** A webhook is an HTTPS URL, the events it wants, and which searches it covers: `scope` `all` (every search, drops included) or `drops` (only searches a drop made), optionally narrowed to one `dropId`. At most 10 per account (`WEBHOOKS_MAX`). Deleting a drop deletes the webhooks narrowed to it, so their scope never widens on its own. `GET /v1/webhooks`, `POST /v1/webhooks` with `{ url, events, scope?, dropId? }` (409 `too_many_webhooks`), `PATCH /v1/webhooks/:id` with any of those plus `enabled`, `DELETE /v1/webhooks/:id`, `POST /v1/webhooks/:id/test`, `GET /v1/webhooks/:id/deliveries` (the last 50).
- **Events.** `lead.ready`: a company with at least one valid address, sent once its checks have settled: no address left unchecked, or the search ended (done, or failed with `quota_exceeded`, which leaves some unchecked). Once per company per webhook. `data` is `{ search: { id, kind, dropId, dropName }, company }`, where `company` has the shape of `GET /v1/searches/:id/companies`, with every checked address. `search.finished`: a search reached `done` or `failed`; `data` is `{ search }` with its counters. Canceling sends nothing. `ping`: only from the test route.
- **Payload.** `POST` with `{ type, timestamp, data }` as JSON. Headers follow Standard Webhooks (standardwebhooks.com), so its libraries verify them: `webhook-id` (the delivery id, the same on every retry; dedupe on it), `webhook-timestamp` (unix seconds) and `webhook-signature` (`v1,` plus base64 HMAC SHA-256 of `{id}.{timestamp}.{body}`, keyed with the base64 part of the secret). The secret is `whsec_` plus 24 random bytes in base64, returned once by `POST /v1/webhooks`. To rotate, make a new webhook and delete the old.
- **Delivery.** The worker sends due deliveries every 2 seconds (`FOR UPDATE SKIP LOCKED`, 20 at once, again while batches come back full). A 2xx within 10 seconds is success; redirects are not followed. Retries after 5 seconds, 5 minutes, 30 minutes, 2 hours, 5 hours, 10 hours and 10 hours, then the delivery fails. A webhook whose delivery fails for good with no success since that delivery was created (a day of failures) is disabled with `disabledReason: 'failing'`; the user turns it on again. Disabling or deleting a webhook drops its pending deliveries.
- **Built when sent.** A delivery row holds only the event and the ids it is about. The payload is built from the current data at each attempt, so a deleted search, an opt-out or an expired search drops the delivery (`skipped`) instead of sending addresses we no longer hold. No address is stored outside `emails`.
- **Safety.** Only `https` URLs on a public address: the host is resolved at create, update and every send, and the request connects to the address that passed. Loopback, private, link local, CGNAT, multicast and reserved ranges (IPv4 and IPv6, mapped addresses included) answer 422 `webhook_url_not_allowed`. `WEBHOOK_ALLOW_PRIVATE=true` lifts that and allows `http` for local development only.
- **Test.** `POST /v1/webhooks/:id/test` sends a signed `ping` from the API at once and returns `{ ok, status, error, durationMs }`. It is not stored.

## Plans

One product for everyone. Every feature is on every plan; a plan is only a monthly allowance of verified emails. The ladder lives in `packages/shared/src/plans.ts` and is shared by the server, the site and the desktop app:

| Plan key (Clerk slug) | Verified emails a month | USD a month |
|---|---|---|
| `free` | 50 | 0 |
| `emails_1000` | 1,000 | 5 |
| `emails_2500` | 2,500 | 9 |
| `emails_7500` | 7,500 | 19 |
| `emails_20000` | 20,000 | 39 |
| `emails_50000` | 50,000 | 79 |
| `emails_100000` | 100,000 | 149 |

- A verified email is an address whose check came back `valid`, generic or personal. Invalid, risky, catch-all and unknown results are free.
- An address the user was charged for is not charged again while its `billed_emails` row exists, which is 12 months (see "Privacy", retention).
- Crawling stores addresses for free, but an address is only returned by the API and the CSV once its check has run. A valid address that no longer fits the allowance stays unchecked and hidden.
- When the allowance is used up, the search stops with status `failed` and error `quota_exceeded`, and new searches are refused with 403. No overage is ever charged. Usage resets each calendar month (UTC); nothing rolls over.
- Plans are Clerk Billing user plans. Checkout and cancel happen on the site at `/desktop/billing`, which the desktop app opens in the browser. The server reads the held plan with the Clerk Backend API (`billing.getUserBillingSubscription`): on `GET /v1/me` when the stored plan is older than 5 minutes, on `?sync=1`, and on every billing webhook. Active and past due items count, a canceled item counts until its period ends, and the most generous plan wins. A slug Clerk reports that the catalog does not know is logged as an error and never drops the user to Free.

## Source costs

Brave Search bills every request, while users pay only for valid emails. A web search that finds nothing still costs requests, so the find job keeps that cost down:

- **Stop early.** The adapter fetches one page (20 results) at a time and the find job stops pulling as soon as the search has `limit` companies, so a search never fetches pages it does not use. At most 10 pages per search.
- **Cache.** Every page is stored in `web_search_cache` by normalized query (trimmed, lowercased, single spaced), country and page, and reused by any search for 7 days (`RETENTION.webSearchCacheDays`). A cache read or write that fails never fails the search.
- **Rate.** `BRAVE_REQUESTS_PER_SECOND` (default 1, the free plan) sets the shared rate limit, with a tenth of headroom. `web` and `domains` searches share one client, so one limit.
- **Refusals.** A 429 whose spent window resets within 5 seconds is waited out (3 tries). A 429 for a long window (monthly quota, the usage limit set in the Brave dashboard) and any 401, 402 or 403 raise `SourceUnavailableError`: the search fails with `source_unavailable` (companies already found keep crawling), Brave is paused in `source_pauses` for 10 minutes and the operator gets an alert. While paused, `POST /v1/searches` refuses web searches with 503 `source_unavailable` and the desktop says web search is paused on our side. When the pause runs out the next web search tries Brave again, so it recovers on its own once the limit is raised. `cli sources resume brave --prod` ends it at once.
- **Alerts.** Operator alerts are emailed through the Day3 API (`DAY3_API_KEY`, `ALERT_EMAIL_TO`, `ALERT_EMAIL_FROM`), each key at most once an hour (`alerts_sent`). Without a key they are only logged. Alerts: a source refusing us, and Brave spend this calendar month passing 80% and 100% of `BRAVE_MONTHLY_BUDGET_USD` (requests counted in `source_requests` times `BRAVE_COST_PER_1000_USD`). `cli alert test --prod` sends a test.
- **Names.** A `domains` search pays only for names: one request each, none for domains, and none for a name looked up in the last 7 days. Its requests count toward the Brave budget like `web`.
- **Measure.** Each search counts its paid requests (`source_requests`) and pages served from the cache (`source_cache_hits`). `cli stats --days 30 --prod` on the VPS prints them per kind next to valid emails, with valid emails per paid request.

## Desktop screens

- **Searches** (home): list with status, counters and progress. A "New search" button.
- **New search**: four tabs (Local businesses, Web search, New launches, Paste a list) with the fields above and a limit. Paste a list has a large monospace field, one item per line, and reads it back as it is typed: how many domains and how many names to look up, and the first few items. A country line appears once the list holds a name. There is no limit field: the list is the limit. Searches of a list are titled by their first items ("linear.app, Pleo and 5 more"). The command bar has "Paste a list of companies". Clipboard lookup, screen OCR, CSV drop (below) and the inbox folder build on this kind.
- **Search results**: table of companies with their emails and verification badges. Filter by verification and email kind, text search, copy email, open website, export CSV (saved via a native save dialog).
  - **Selection.** Click selects a row, Cmd/Ctrl click toggles one, Shift click selects the range from the last plain click, Cmd/Ctrl Shift click adds that range. Cmd/Ctrl+A selects every loaded row; Escape, a click on empty canvas or the bar's close button clears. Changing a filter clears it. A glass bar above the dock counts the selection.
  - **Drag out.** Dragging a selected row drags the whole selection; dragging any other row drags that row alone. The renderer builds the CSV (export columns, one row per email, a company without emails gets one row with blank email fields, UTF-8 BOM, formulas defused like the server export) and sends it on `leads:start-drag-csv`. Main checks it (a string, at most 16 MB, the name cleaned like the export's), writes it to `<temp>/nvoke-drag/<uuid>/<name>.csv` and calls `webContents.startDrag` with the OS icon for .csv files. It drops into Excel, Outlook, a CRM in the browser or a folder. Drag folders older than a day are removed at launch and on each drag. The file is named `<domain>.csv` for one company, `nvoke-<search>-<n>.csv` for several.
  - **Copy.** Cmd/Ctrl+C copies the selection as tab separated text with a header row, same columns and rows as the drag, so a paste into a spreadsheet keeps the columns. Tabs and line breaks inside a value become spaces. Selected text and focused fields keep the normal copy.
- **CSV drop.** Drop a .csv, .tsv or .txt on the window (XLSX is refused with a hint to save as CSV UTF-8; up to 5 MB): while the file is over the window a glass target says so, then a dialog names the file, lets the user pick the column (guessed: cells that read as domains first, then a header like website or domain, then company or name) and shows the domains and names it found, with a country line when there are names. "Find contacts" starts a `domains` search with the unique items of that column, cut at the plan's search limit (the dialog says how many were left out). The renderer reads the file's text and parses it (quotes, `,` `;` or tab, header row detected). Its path comes from `webUtils.getPathForFile` in the preload (`files.pathFor`). When the search is `done`, the renderer fetches every company and sends the original's path and the CSV to main (`files:save-enriched`). Main accepts an absolute path to an existing .csv, .tsv or .txt file and a CSV of at most 16 MB, and writes `<name>.nvoke.csv` in the same folder itself (replacing an earlier copy, never `.nvoke.nvoke.csv`). The copy is the original columns plus `domain`, `email`, `kind` and `verification` (prefixed `nvoke_` when the file already has that column): one row per email, a row without a match keeps its cells with blank new ones, formulas in new cells are defused. A toast says how many companies have a valid address and offers Show in folder (`files:reveal`, only for `.nvoke.csv` files). The search shows in Searches like any other. Jobs are held by the renderer: quitting the app before the search finishes means no copy (the search and its export remain). In a plain browser (mock) the copy downloads instead.
- **Inbox folder.** An optional watched folder, off until the user turns it on under Account, `Documents/nvoke/inbox` unless they pick another (Change opens a native folder picker in main, a drive root is refused; Open shows it). Main (`src/main/inbox.ts`) looks at it every 2 seconds for .csv, .tsv and .txt files (not hidden files, `~$` locks, partial downloads or `.nvoke.csv` copies) and takes a file on the second look that sees the same size and modified time, so a copy in progress is left alone. A file whose enriched copy is already in the done folder is skipped, a file over 5 MB gets a notification, and files wait with a notification while nobody is signed in and are taken at the next sign-in. Main reads the file and pushes it to the renderer (`inbox:file`, with an opaque id, never a path), which enriches it like the CSV drop with the guessed column, cut to the lower of the search limit and what is left of this month's allowance (`/v1/me`): `usage.emailsLimit - usage.emailsVerified`, none left means a quota notification. When the search is done the renderer sends the CSV back (`inbox:done`); main writes `name.nvoke.csv` to the done folder (`nvoke/done` beside an inbox called `inbox`, else `done` inside the chosen folder), moves the original to `done/originals` (renamed `name (2).csv` when taken) and shows a native notification, whose click shows the file. A failed search, an empty column or a quota error (`inbox:failed`) is a notification and the file stays in the inbox until it changes. It runs while the window is hidden in the tray, as long as the app is signed in.
- **Drops**: the user's drops with what each delivered and when it runs next, and the feed's last week per source. Each drop has Edit, Check now, Pause or Resume and Delete. The editor is a sentence like New search: "Watch [keyword] from [sources] up to [N] a day called [name]". The searches a drop makes appear in Searches with the drop's name; their menu has Open drop instead of Run again.
- **Account**: user, plan, verified email meter, appearance, Open at login, Quick search shortcut, Inbox folder, Drop notifications, sign out (with what the local copy holds and when it last synced), Use nvoke in Claude and Cursor (below), Upgrade or Manage billing (opens `/desktop/billing` on the site), and API keys (create, shown once, revoke) with the MCP setup line.
- **Tray** (menu bar on macOS): nvoke lives there while it runs. The menu has Open nvoke, New search, today's drop line ("Today’s drops: 12 leads", the verified emails from drop searches made since local midnight, read from `GET /v1/searches`; it opens that search, or Searches when there are several) and Quit nvoke. On Windows and Linux a click on the icon opens the window. Closing the window hides it and keeps nvoke running; the first close says so once in a notification. Quit from the tray (or Cmd+Q) ends it.
- **Open at login**: a switch on Account, on by default once the user first signs in. The app then starts hidden in the tray with no window (`--hidden` on Windows and Linux, `wasOpenedAtLogin` on macOS). Windows and macOS use the OS login item, Linux an XDG autostart entry. Development builds save the setting but never register. Kept in `userData/desktop-settings.json`.
- **Quick search**: a global shortcut (default Ctrl+Shift+Space on Windows and Linux, Cmd+Shift+Space on macOS, changeable on Account) opens a small frameless glass window, centered on the display under the pointer, over whatever app is in front. It is the command bar again (`Commands` in `CommandBar.tsx`, loaded by the same renderer on `#/quick`): type to jump to a search or run an action, and screens open in the main window. When the clipboard holds one domain, URL or email address at the moment the window opens, the first row is "Find contacts at acme.com" and Enter runs a one-domain search of kind `domains` (limit 1); the window then lists the addresses as they arrive, each with a copy button (invalid ones left out). The clipboard is read once, in main (`src/main/clipboard-lookup.ts`), when the window is shown, never in the background, and only a clean domain, URL or email passes (prose, lists and long text are ignored); the quick window gets the result with `quick:shown`. Above it sits "Who runs this site" with the domain of the browser tab that was in front when the shortcut was pressed, which runs the same one-domain search. The tab is read only on the shortcut, in main (`src/main/front-tab.ts`), and arrives a moment after the window shows with `quick:front-tab`; when the tab and the clipboard name the same site there is one row. Windows: a short PowerShell script (UI Automation, part of Windows, nothing installed) walks the top level windows front to back, skips nvoke's own and topmost ones, and when the first is Chrome, Edge, Firefox or Brave reads its address bar (about 0.7 s). macOS: the window list names the app in front without any permission; for Safari, Chrome or Arc AppleScript returns the front tab's URL. That needs the user's Automation permission, so the first time per browser the row says macOS will ask, and Enter (`quick:read-front-tab`) shows the system prompt (text from `NSAppleEventsUsageDescription` in `electron-builder.yml`) while the window stays up, then starts the search. Browsers already asked are kept as `automationAsked` in `userData/desktop-settings.json` and read without asking; a refusal turns the row into a pointer to System Settings, Privacy & Security, Automation. Other apps, browser pages (`chrome://`, `about:`, files) and Linux give no row. Typing text adds a first row that starts a search on Enter: "dentists in Aarhus" (or "near") is a local search, anything else a web search. The window then shows the search's progress, and Open in nvoke (Enter) brings up the main window on it. Esc, a click elsewhere or the shortcut again hides it and the previous app keeps focus (macOS: nvoke hides itself). Signed out it offers Open nvoke. The shortcut works while nvoke sits in the tray. Registration is `globalShortcut` in `src/main/quick-window.ts`; if another app holds the shortcut, the old one stays and Account shows the clash. The accelerator is validated in `src/ipc/accelerator.ts` (modifier plus key) and kept as `hotkey` in `userData/desktop-settings.json`. Channels: `desktop:set-hotkey`, `quick:hide`, `quick:open-in-main` (route hash), `quick:set-height`, `quick:shown`, `quick:front-tab`, `quick:read-front-tab`; the quick channels only answer the quick window.
- **Local copy**: the main process keeps the signed-in user's searches, companies and checked emails in SQLite (`node:sqlite`, which Electron ships) at `userData/leads.sqlite` (`apps/desktop/src/main/local`). A finished search's results open from it at once, and text search and the verification and kind filters run on it in milliseconds over 50k+ companies, with the same semantics as `GET /v1/searches/:id/companies`. A running search reads the API live. Sync runs in the background: `GET /v1/searches` every minute (every 10 seconds while a search runs), then every page of companies for each search that finished or changed, was opened, or was last fetched 6 hours ago, at most 8 searches a pass. Offline, the searches list, search details and results come from the copy, and Searches and the results dock say "Offline, synced 42 min ago". No new API: the copy is built from the existing routes. The renderer reads it through `window.nvoke.local` (`src/ipc/contract.ts`).
- **Local MCP** ("Use nvoke in Claude and Cursor" on Account): Claude Desktop, Claude Code and Cursor get the MCP tools through the app's own sign-in, with no API key. Main listens on a local pipe (`\\.\pipe\nvoke-mcp-<12 hex of sha256(userData)>` on Windows, `userData/mcp.sock` with mode 0600 elsewhere) and runs one MCP session per connection (`@modelcontextprotocol/sdk`, newline delimited JSON like stdio). Tools and instructions are `MCP_TOOLS` and `MCP_INSTRUCTIONS` from the catalog, run by `runMcpTool` (`packages/shared/src/mcp.ts`, shared with `POST /mcp`) through `AuthSession.api`, so the device token never leaves main. Signed out, every tool answers an error asking the user to sign in. Clients start `mcp-launcher.js` (built beside the main bundle, unpacked from the asar) with the app binary in Node mode: `ELECTRON_RUN_AS_NODE=1 nvoke mcp-launcher.js <pipe> [app args]`. It relays stdio to the pipe; when nvoke is not running it starts it with `--hidden` and waits up to 20 seconds. Account shows the clients connected now (from `clientInfo` at initialize, pushed on `mcp:clients-changed`), an Add to Claude Desktop button, the `claude mcp add nvoke --scope user ...` line for Claude Code and the JSON for Cursor's `~/.cursor/mcp.json`. Add to Claude Desktop asks in a native dialog, then sets `mcpServers.nvoke` in `claude_desktop_config.json` (`%APPDATA%\Claude`, the Store build's package folder when it exists, `~/Library/Application Support/Claude` or `~/.config/Claude`), keeps every other key, writes through a temp file and refuses a file that is not a JSON object. Without Claude Desktop's folder the button becomes Get Claude Desktop. Code: `apps/desktop/src/main/mcp`, `src/main/mcp-launcher.ts`, `components/LocalMcp.tsx`.
- **Drop notifications**: main polls `GET /v1/searches` every minute while signed in (no new endpoint). A finished `drop` search with at least one valid email raises a native notification titled with the drop's name, "14 new launches, 9 valid emails", once per search; clicking it focuses the window and opens that search. The count of valid emails in finished drop searches not yet opened is the dock badge on macOS, an overlay icon with that number on the Windows taskbar button (drawn in main, 99 at most) and the launcher count on Linux. Opening a search (by hand or by the click) clears its share. The first poll after signing in only records what exists, so old deliveries never badge or notify. No toast shows while the nvoke window is focused; otherwise the OS applies Focus (macOS) or Focus Assist (Windows). State (the setting, announced and seen search ids) lives in `userData/notifications.json` and is reset on sign out. Channels: `notifications:get-settings`, `notifications:set-enabled` (boolean, validated), `notifications:mark-seen` (uuid, validated), and the push `notifications:open-search`.

## Privacy

Full documents: `docs/legal/` (`lia.md` legitimate interest assessment, `dpia.md`, `ropa.md` record of processing, `article-14.md`, `lawyer-brief.md` with the open questions). Background research: `docs/research/gdpr-competitors.md`. Rights requests: `deploy/PRIVACY-RUNBOOK.md`.

- **Positioning.** nvoke is a prospecting research tool, never a "cold email" tool. In Denmark, Markedsføringsloven §10 requires prior consent for marketing email to anyone, B2B, info@ and employees included. Customers are bound to it by the terms. nvoke itself never sends email.
- **Roles and basis.** nvoke is controller for collection, classification, verification, the shared cache and the suppression list, on legitimate interest (Art 6(1)(f)). The customer is an independent controller for its own use of what it views and exports.
- **Collection.** Only addresses published on the company's own public pages, within the crawl limits in the pipeline. robots.txt honoured, no logins, no CAPTCHA solving, named user agent linking to `/bot`. No names, titles or social profiles are extracted.
- **Split cache.** Only generic addresses are shared between users (`domain_emails`). Personal addresses exist only in the `emails` of the search that found them and are deleted with it.
- **Suppression.** `suppressions` is checked before storing a crawl result, before serving from the cache and before export. An opt-out or erasure (`apps/server/src/privacy/erase.ts`) suppresses first, then deletes every stored copy: `emails`, `domain_emails`, `domains`, `email_checks`, `billed_emails` and, for a domain, the companies found on it (subdomains included). Shared mailbox domains such as gmail.com cannot be suppressed as a whole from the public page. Sources: the public `/opt-out` page and API, the `/bot` page, privacy@nvoke.run, and admin (`cli privacy suppress-domain`).
- **Retention**, enforced by `purge()` in the worker (hourly):
  - `domain_emails`: deleted 12 months after `first_seen` (never reset by a new search or recrawl), and as soon as a recrawl no longer finds the address.
  - `searches` with their `companies` and `emails`: deleted 12 months after `created_at`, or earlier when the user deletes the search.
  - `email_checks`: 30 days.
  - `web_search_cache`: 7 days after `fetched_at`.
  - `feed_items`: 90 days after `discovered_at`. Erasing a domain deletes its feed items too.
  - `webhook_deliveries`: 30 days after `created_at`. They hold ids only, never addresses.
  - `billed_emails`: 12 months after `billed_at`. Finding the address again after that charges it again.
  - `domains`: dropped 12 months after `recheck_at` when no search crawled the domain again.
  - `suppressions`: forever, so an opted-out address is never collected again.
- **Desktop local copy.** The desktop app keeps a copy of what the API returns for the signed-in user (searches, companies, checked emails) in `leads.sqlite` in the app's user data folder, unencrypted and protected by the OS account like any document. It mirrors the API: each search is fetched again at least every 6 hours while the app runs and online, and the fetch replaces its companies, so an address removed by an opt-out, an erasure or retention leaves the copy on the next fetch. A search the API no longer lists (deleted, purged after 12 months, or past the newest 200) is deleted locally on the next sync, which runs every minute. Deleting a search in the app drops it locally at once. Signing out, including a sign out forced by a revoked session, deletes the file. The copy is never sent anywhere.
- **Transparency.** Article 14 notice on `/privacy` (Danish and English). No individual notification today; whether personal addresses need one is open (`docs/legal/article-14.md`).
- **Rights.** Access, erasure and objection by email to privacy@nvoke.run, handled with `cli privacy export`, `cli privacy erase` and `cli privacy suppress-domain`. Access answers name the source URL of every address.
- **Open items** (details in `docs/legal/`): Article 14 for personal addresses, §10 co-liability, SMTP probes, source terms of use, whether `billed_emails` should hold hashes instead of plain addresses, Supabase region and VPS host. Webmail addresses (gmail.com and similar) are always classified personal and never cached.
