# API (Fastify, all under `/v1`, all require an authenticated user unless marked public)

- `POST /v1/searches` with `{ kind, params, limit?, checkInboxes? }` returns the search. `checkInboxes` (default false) checks all of its role inboxes, not only the one fallback inbox a company with no valid personal address gets ([pipeline](pipeline.md) step 4). Kind `domains` takes `params: { items, country? }`. While Brave is paused it is refused only when the list holds a name. Kind `icp` takes `params: { description, product?, countries?, locations? }` and is refused while Brave is paused.
- `GET /v1/searches` returns the user's searches, newest first.
- `GET /v1/searches/:id` returns one search with counters.
- `POST /v1/searches/:id/cancel`
- `PATCH /v1/searches/:id` with `{ ongoing?, checkInboxes? }`, at least one. `ongoing` switches daily rounds on or off (see [Describe your customer](sonar.md)). Only `icp` searches: other kinds answer 400 `ongoing_not_supported` and nothing changes. The API defaults `ongoing` to false; the web app and the desktop app switch it on for the `icp` searches they start. `checkInboxes` works on every kind: on sets `searches.check_inboxes`, clears `skipped = 'role_inbox'` on the search's unchecked role inboxes at companies with no valid personal address (the policy would skip the others again at once) and queues a verify job at priority -10 for every unchecked role inbox with no queued one (so switching on again recovers a check that got lost), [pipeline](pipeline.md) step 4. The valid ones show up as they settle and only those are charged, like any verified email; off only stops future checks. Switching on is refused on a canceled search (400 `search_canceled`) and once the allowance is used up (403 `quota_exceeded`, with `billingUrl`). Both the switch and the worker's check decision lock the search row before the address, and the decision writes a `role_inbox` skip only while the switch is still off, so a skip never lands from a stale read. `Search.inboxesSkipped` counts what switching on would check and `inboxesPending` what is still to settle; `Company` carries the same two counts. The company list and the CSV still hide every unchecked address. The apps offer it as "Check shared inboxes for this search" under the Shared inboxes pill, with how many it checks, that only valid ones count and how many verified emails are left (a warning when that is fewer), and next to a company with no named person that has a skipped inbox.
- `POST /v1/searches/:id/more` with `{ kind, params, limit? }` (the search's own kind, else 400 `kind_mismatch`) runs an ended search again into the same list ([pipeline](pipeline.md) step 6). 409 `search_running` while it runs; quota and Brave pause as for a new search.
- `DELETE /v1/searches/:id` deletes it with its companies and emails.
- `GET /v1/searches/:id/companies?cursor=&verification=&kind=&q=` returns companies with their emails, paginated.
- `GET /v1/searches/:id/companies/:companyId` returns one company with its emails. `PATCH` the same path with any of `name`, `location`, `phone`, `category` (null clears one, not the name) and `opener` (the user's own line, status `done`; null removes the opener). `DELETE` it removes the company with its emails, and `DELETE /v1/searches/:id/companies/:companyId/emails/:emailId` removes one email. Both deletes count the search again (`companies_found`, `companies_crawled`, `emails_found`, `emails_valid` from the rows, like an erasure); a charged email stays charged. Every edit and delete stamps the search's `edited_at` (`editedAt`, migration `1880_lead_edits`), which is part of the desktop copy's fingerprint, so it fetches the search again.
- `GET /v1/searches/:id/export.csv` returns one row per email: company, domain, website, email, kind, verification, source_url, location, phone, opener (the company's drafted line when it is `done`, else blank).
- `POST /v1/searches/:id/openers` with `{ companyIds?, redo? }` queues openers and returns 202 `{ queued, skipped }`: see [Openers](openers.md).
- `GET /v1/me` returns user, plan and usage for this period, how the request authenticated (`via`), the account's origin (`account`) and `billingUrl`. `?sync=1` re-reads the plan from Clerk Billing first.
- `GET /v1/plans` (public) returns the plan ladder.
- `GET /v1/site-profile`, `POST /v1/site-profile` with `{ website }`, `PATCH /v1/site-profile` with any profile fields, `DELETE /v1/site-profile` (204): see [Site profile](site-profile.md).
- `GET /v1/api-keys`, `POST /v1/api-keys` with `{ name }`, `GET /v1/api-keys/:id`, `PATCH /v1/api-keys/:id` with `{ name }` (rename, the secret stays), `DELETE /v1/api-keys/:id`: see [API and agents](api-and-agents.md).
- `POST /v1/agents/signup` (public, rate limited) and `POST /v1/agents/claim` (Clerk session): see [API and agents](api-and-agents.md).
- `GET /v1/openapi.json` (public): OpenAPI 3.1 for every route.

- `GET /v1/drops` (and `GET /v1/drops/:id` for one) returns the user's drops (with `companiesDelivered`) and per feed source whether it is collected and how many launches it brought in over the last 7 days. `POST /v1/drops` with `{ name, keyword?, sources?, dailyLimit? }` (409 `too_many_drops` past 20), `PATCH /v1/drops/:id` with any of those plus `enabled` (`keyword: null` removes it), `POST /v1/drops/:id/run`, `DELETE /v1/drops/:id`. Schemas in `packages/shared/src/drops.ts`.
- `GET /v1/webhooks`, `GET /v1/webhooks/:id`, `POST /v1/webhooks`, `PATCH /v1/webhooks/:id`, `DELETE /v1/webhooks/:id`, `POST /v1/webhooks/:id/test`, `GET /v1/webhooks/:id/deliveries`: see [Webhooks](webhooks.md).
- `POST /v1/local-crawl/claim` and `POST /v1/local-crawl/results`: see [Local render crawl](local-render-crawl.md).
- `POST /v1/privacy/opt-out` (public, rate limited) with `{ email }` or `{ domain }` suppresses it at once and deletes matching data. No confirmation step. Always returns `{ ok: true }`, so it cannot be used to test whether nvoke holds an address. Schema in `packages/shared/src/privacy.ts`.
- `POST /v1/tools/verify-email`, `POST /v1/tools/extract-emails`, `POST /v1/tools/email-auth` (public, rate limited): see [Free tools](free-tools.md).

Outside `/v1`: `GET /site-shots/<token>.jpg` (public, a site profile screenshot), `POST /mcp` (the MCP server), `/.well-known/oauth-protected-resource[/mcp]` and `/.well-known/oauth-authorization-server` (OAuth discovery for MCP clients), and `POST /webhooks/clerk` takes Clerk Billing events (signed with `CLERK_WEBHOOK_SIGNING_SECRET`) and re-reads the paying user's plan.

Request and response shapes live as zod schemas in `packages/shared/src/leads.ts` and are the single source of truth for server and desktop. The desktop polls `GET /v1/searches/:id` every 2 seconds while a search is running.
